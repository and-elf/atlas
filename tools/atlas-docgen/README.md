# atlas-docgen

All Atlas platform tools are prefixed `atlas-` (library naming convention extended to tools), with the tool's C++ namespace matching the suffix (`atlas::docgen`, mirroring `atlas::cgen`/`atlas::rcc`/`atlas::core`).

**Name reasoning:** spec §12 (Build Model) lists "documentation generation" as its own distinct Atlas Tooling responsibility, separate from contract generation, reflection generation, and resource compilation. `atlas-cgen` already claims the short suffix that would most obviously read as "the docs tool" if abbreviated the same way (`-cgen` is "contract gen"), so this tool takes `docgen` in full rather than colliding with or overloading that convention — it names exactly what the tool does (generates docs) the same way `atlas-rcc` ("resource compiler") reads as exactly what it does, and is unambiguous next to `atlas-cgen`/`atlas-rcc` in a directory listing.

**Status:** Implemented for the manifest shape `atlas-cgen` already parses (`capability.name`, `depends_on`, `consumes`, `properties`/`requests`/`events`, including the optional `composition:`/`trigger:` property annotations, spec §20). Given one or more capability manifest YAML files, emits one Markdown reference page per manifest, each describing that capability's dependencies and its properties/requests/events with their fields. Verified against the real `health`, `armor`, and `cosmetics` fixtures under `tests/fixtures/` (the same ones `atlas-cgen`'s own tests use) both as unit tests asserting on the generated text (`tests/atlas-docgen/markdown_writer_test.cpp`) and by running the actual `atlas-docgen` binary against those fixture files end-to-end.

**Provides:** human-readable reference documentation generation from capability manifests (spec §12's "documentation generation" Atlas Tooling responsibility).

**Spec:** [§12 Build Model](../../docs/specification/12-build-model.md) ("documentation generation" as a distinct Atlas Tooling responsibility), [§13 Library Architecture — Capability Manifest](../../docs/specification/13-library-architecture.md), [§20 Property Composition](../../docs/specification/20-property-composition.md) (composition strategies and triggered properties, both annotated in the generated output)

## Scope

Deliberately narrow, matching the project's established discipline (`tools/atlas-cgen/README.md`, `tools/atlas-rcc/README.md`) of shipping one minimal real slice rather than the eventual full scope:

- **Parses nothing itself.** `atlas-docgen` links `atlas-cgen-lib` and calls its already-implemented, already-tested `atlas::cgen::parse_manifest`/`atlas::cgen::Manifest` directly, rather than reimplementing YAML parsing a second time for what is exactly the same manifest shape `atlas-cgen` already consumes. See "Dependency position" below for why this is a normal, intended dependency rather than a layering violation.
- **Output shape: one Markdown page per manifest**, not a single combined reference document. This mirrors `atlas-cgen`'s own "one manifest in, one generated artifact out" single-capability mode exactly (`generate_contract`/`generate_markdown_doc` have the same two-name signature: a manifest plus cosmetic `header_name`/`source_name` strings for the "GENERATED"/"Source:" comment). A per-capability page keeps the generation function easy to unit-test in isolation (assert on one manifest's rendered text, not on where it landed inside a larger aggregated document) and scales to a project with many capabilities without the generator needing to know about all of them at once — a combined reference document, if wanted later, is a straightforward second CLI mode built on the same per-manifest rendering function (an `--index` mode that also emits a table-of-contents page linking the per-capability ones), not a redesign. A single combined document was considered and rejected for this round on exactly this basis: it would need to be regenerated in one invocation seeing every manifest at once, whereas the per-page design lets a build regenerate exactly the pages whose source manifest actually changed.
- **CLI: `atlas-docgen <output-dir> <manifest.yaml>...`** — takes one output directory and one or more manifest paths, writing `<output-dir>/<capability_name>.md` for each. This is the "one or more capability manifests" the issue asks for, built directly on the per-manifest `generate_markdown_doc` function: the CLI loop is the only thing that's plural, mirroring how `atlas-cgen --host` already loops over a variadic capability-path list in its own `main.cpp`.
- **Field types are rendered as the manifest declares them** (`int32`, `EntityRef`, `ResourceId`, ...), not their mapped C++ spelling (`std::int32_t`, `atlas::EntityRef`). This is a reference document about a capability's declared *manifest* structure, not about the generated C++ contract `atlas-cgen` produces from it — a capability author reading this page thinks in manifest vocabulary, the same vocabulary they authored the YAML in. `atlas::cgen::map_field_type` is used exactly once, indirectly: `parse_manifest` already validates every field type against it before `atlas-docgen` ever sees a `Manifest`, so by the time `generate_markdown_doc` runs, every field type is already guaranteed to be one of the small closed set `atlas-cgen` maps — `generate_markdown_doc` does not re-validate this itself, it only renders.
- **Composition/trigger annotations, no strategy-specific rendering.** A composed property gets a `_Composition strategy: <Name>_` line and a triggered property gets a `_Triggered: ...` line, both ahead of that property's field table — mirroring `atlas::cgen::contract_writer`'s own "composition/trigger member emitted before ordinary fields" convention for the analogous generated C++ struct. Composed and triggered are independent (spec §20: a property may declare either, both, or neither), so each line is rendered independently rather than as a combined/mutually-exclusive case. The seven composition strategy names themselves are rendered verbatim from the manifest's raw token (already validated by `parse_manifest` via `atlas::cgen::map_composition_strategy`) — no strategy gets special-cased prose here, matching `atlas-cgen`'s own "declared exhaustively even though only Additive has a working evaluator" stance: this is documentation of what the manifest declares, not commentary on what's implemented.
- **Empty sections are omitted, not shown as empty.** A capability with no `requests:` block gets no "## Requests" heading at all, rather than an empty one — the same "omit rather than show a hollow placeholder" instinct `atlas-cgen`'s own README documents for its `DependsOn` assertion. `depends_on`/`consumes` are the one exception: those two lines always appear, rendering `_(none)_` when empty, because "this capability declares no dependencies" is itself a fact worth stating explicitly on every page, unlike a property/request/event section, which has no meaningful "empty" state to assert.
- **Does not validate or resolve `depends_on`/`consumes` against a project-wide graph.** Each name is rendered exactly as declared, with no attempt to confirm it resolves to a real composed capability, detect cycles, or link to that capability's own generated page — `atlas-cgen`'s host composition mode (`dependency_graph.hpp`/`property_graph.hpp`) already owns that validation; duplicating it here to decorate documentation would be doing someone else's job. A future host-aware mode that cross-links pages and confirms every named dependency actually has a page is a natural follow-up once a real multi-page documentation set exists to make that worth building.
- **Does not process `version`/`source`/`contracts`.** Same as `atlas-cgen`'s own single-capability mode: these manifest keys are real (spec §13) but not parsed by `atlas::cgen::Manifest` yet, so there is nothing for this tool to render from them either. Widening `atlas::cgen::Manifest` to carry them is `atlas-cgen`'s job, not this tool's — `atlas-docgen` picks up whatever `Manifest` already exposes.
- **No templating system.** Unlike `atlas-cgen`'s `templates/*.tmpl` + `template_engine.hpp` (needed there because the generated output is C++ source with a fixed, syntax-sensitive shape), the Markdown here is assembled directly by ordinary C++ string-building functions (`render_name_list`, `render_annotations`, `render_fields_table`, `render_block`) in `src/markdown_writer.cpp` — introducing a second templating layer for a much simpler, less structurally rigid text format would be exactly the "over-engineering a templating system" the issue calls out to avoid. If the output format grows real conditional/repetition complexity later, `atlas-cgen`'s template engine is right there to reuse (it's a generic `{{PLACEHOLDER}}` substitution function, not `atlas-cgen`-specific) — not duplicated speculatively now.
- **`main.cpp` (the CLI)** is excluded from the coverage gate (`cmake/CodeCoverage.cmake`'s existing `tools/[^/]+/src/main.cpp` glob already covers it without modification), matching `atlas-cgen`'s and `atlas-rcc`'s convention — its argv/file-I/O error paths need subprocess-spawning test infrastructure this project doesn't build yet. The library logic it wires together (`atlas::cgen::parse_manifest`, `generate_markdown_doc`) is fully unit-tested in `tests/atlas-docgen/`.

## Dependency position

Depends on `atlas-cgen-lib` (`atlas::cgen_lib`) for `atlas::cgen::Manifest`/`parse_manifest` — a deliberate, direct reuse of an existing runtime-adjacent tooling library, not a new YAML dependency: `atlas-docgen` does not fetch or link `yaml-cpp` itself. This is the same relationship `tests/atlas-contracts` already has with `atlas-cgen`'s generated output (see `tools/atlas-cgen/README.md`) applied one layer up — one tool consuming another tool's already-validated parsed structure, rather than every manifest-consuming tool re-parsing YAML independently. `atlas-docgen` does not depend on, and is never depended on by, any `atlas-*` runtime or capability library: like `atlas-cgen` and `atlas-rcc`, it is build-time tooling, not something a running host links against.

## Contract generation, resource compilation, and documentation generation

Spec §12 lists these as three separate Atlas Tooling responsibilities, and this repository now has one tool for each: `atlas-cgen` emits the generated C++ contract *shape* a capability's properties/requests/events compile against; `atlas-rcc` compiles authored resource *data* into `ResourceId` tables; `atlas-docgen` emits human-readable *documentation* describing a capability's manifest-declared structure for people, not the compiler. All three read the same kind of source-of-truth authored YAML, but produce artifacts serving entirely different consumers (the C++ compiler, a running host's resource resolution, and a person reading a reference page) — `atlas-docgen` will never need to depend on `atlas-rcc`, or vice versa, for the same reason `atlas-cgen`'s own README gives for staying separate from resource compilation.
