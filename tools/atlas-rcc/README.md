# atlas-rcc

All Atlas platform tools are prefixed `atlas-` (library naming convention extended to tools), with the tool's C++ namespace matching the suffix (`atlas::rcc`, mirroring `atlas::cgen`/`atlas::core`).

**Status:** Seeded (issue #33), plus a real packing step (issue #66), CLI wiring for it, and animation-specific manifest metadata (issue #45). Given a resource manifest YAML (a `resources:` list of `name`/`type`/`path` entries, each optionally carrying an `animation:` block), parses and validates it, then compiles it into an in-memory table of `atlas::ResourceId` (spec §3, Resource: "resources are resolved through generated metadata rather than hard-coded paths") plus the type/path resolution data a downstream host needs. Additionally now packs a compiled entry list's real asset files into a self-describing binary blob (`pack_resource_blob`) that `atlas::resource::ResourceRegistry` loads at runtime, and the CLI actually writes one `.blob` file per asset type to disk — see "What's implemented" below. Does not yet emit a generated C++ header — see "Deliberately deferred" below.

**Provides:** resource manifest parsing/validation (including animation-specific resolution metadata), in-memory `ResourceId`-keyed resource compilation, and packing compiled entries' real asset bytes into a loadable blob (spec §12's "resource compilation" tooling responsibility).

**Spec:** [§12 Build Model](../../docs/specification/12-build-model.md) ("resource compilation" as a distinct Atlas Tooling responsibility from contract generation), [§3 Architectural Definitions](../../docs/specification/03-architectural-definitions.md) (Resource: stable identity, never a hard-coded path, scoped to what the composing host actually references), CLAUDE.md's "Naming convention" paragraph (`atlas-rcc`, turning authored asset lists into compiled `ResourceId` tables)

## Scope

Deliberately narrow, matching this project's established discipline of shipping one minimal real slice rather than the eventual full scope (the same discipline `tools/atlas-cgen/README.md` documents for its own first round):

- **Manifest shape.** A resource manifest is a single top-level `resources:` sequence, each entry a mapping of exactly three required fields:

  ```yaml
  resources:
    - name: characters/hero/mesh
      type: Mesh
      path: characters/hero/mesh.fbx
    - name: characters/hero/texture
      type: Texture
      path: characters/hero/diffuse.png
  ```

  `name` is the resource's stable identity — what `atlas::ResourceId::from_name` hashes — never derived from `path`. `type` is an open-ended asset-kind tag (`Mesh`, `Texture`, `Sound`, ...); unlike `atlas-cgen`'s closed field-type table (which maps a fixed set of C++ vocabulary types), a resource `type` is downstream, capability-authored vocabulary this tool has no reason to constrain to a fixed list. `path` is carried through exactly as authored — this tool never resolves, normalizes, or checks it against the filesystem (see "Deliberately deferred").

- **Animation resolution metadata (issue #45).** Any entry may additionally carry an optional `animation:` block — resolution *data* an animation loader needs to find and wire up a clip, not an interpretation of the clip's actual content (spec §24/§2's mechanism/meaning boundary: no parsing of FBX curves, glTF animation channels, or any other animation file format):

  ```yaml
  resources:
    - name: characters/hero/run_cycle
      type: Animation
      path: characters/hero/run_cycle.fbx
      animation:
        skeleton: characters/hero/skeleton   # a name resolving to another resource's ResourceId
        loop: true
        playback_rate: 1.0
  ```

  `skeleton` is a resource *name*, resolved to an `atlas::ResourceId` the same way the entry's own `name` is (`ResourceId::from_name`) — not carried through as a raw string, since a skeleton reference needs to actually resolve against another compiled resource. `loop` and `playback_rate` are optional, each with a sensible default (`false` / `1.0`) — only `skeleton` is required once the block is present at all. **Deliberately not gated on `type == "Animation"`** — this tool has no closed vocabulary to validate `type` against (see "Real discoveries" below), so `animation:` is parsed whenever it's present on an entry, regardless of that entry's `type` string. A `Skeleton`-typed entry needs no changes at all — it's already fully representable as a plain `name`/`type`/`path` entry, with nothing skeleton-specific added anywhere in this round.

- **Validation** (`atlas::rcc::parse_resource_manifest`, `include/atlas/rcc/resource_manifest.hpp` / `src/resource_manifest.cpp`): rejects, with a specific `std::invalid_argument` message naming exactly what was wrong, rather than guessing at intent —
  - malformed YAML (a `YAML::Exception` wrapped with context, same convention as `atlas-cgen`'s `parse_manifest`)
  - a non-mapping document root
  - a missing or non-sequence `resources:` key
  - a non-mapping entry
  - an entry missing `name`/`type`/`path`, or carrying an empty value for one
  - an entry carrying any field beyond the four recognized ones (`name`/`type`/`path`/`animation`)
  - two entries declaring the same `name` (resource identity must be unique across a manifest — a duplicate would either silently overwrite or silently alias in the compiled table, either of which is a real correctness bug, not a warning)
  - an `animation:` value that isn't a mapping
  - an `animation:` block missing `skeleton`, or carrying an empty `skeleton` string (same "empty value" rule the top-level fields already enforce; `skeleton` has no useful default, unlike `loop`/`playback_rate`)
  - an `animation.loop` that isn't a boolean
  - an `animation.playback_rate` that isn't a number, or is `<= 0` (a non-positive playback rate is nonsensical)
  - an `animation:` block carrying any field beyond the three recognized ones (`skeleton`/`loop`/`playback_rate`), mirroring the top-level "unrecognized field" rule

  An empty `resources: []` list parses successfully as zero entries — a manifest that legitimately declares no resources yet is not itself an error.

- **Compilation** (`atlas::rcc::compile_resource_table`, `include/atlas/rcc/resource_table.hpp` / `src/resource_table.cpp`): turns a validated `std::vector<ResourceEntry>` into a `ResourceTable` (`std::unordered_map<atlas::ResourceId, CompiledResource>`), keyed by `atlas::ResourceId::from_name(entry.name)` — the same id a running host would compute to look a resource up. `CompiledResource` is a plain aggregate (Rule of Zero) carrying the id back out alongside `name`/`type`/`path`, since the id itself doesn't reproduce the name it was derived from. An entry carrying `AnimationMetadata` compiles into an optional `CompiledAnimationMetadata` (`skeleton` resolved to an `atlas::ResourceId` the same way `entry.name` itself is, plus `loop`/`playback_rate` carried through unchanged) — `compile_resource_table` does **not** check that `skeleton`'s name actually corresponds to another entry in the same manifest; that's a resolution-time (running host) concern, consistent with this tool's existing "no path existence checking" stance (see "Deliberately deferred" below).

- **`atlas::rcc::pack_resource_blob`** (`include/atlas/rcc/resource_blob.hpp` / `src/resource_blob.cpp`, issue #66) — the first place this tool touches real asset bytes rather than just carrying `path` through as an opaque string. Given a list of already-compiled `CompiledResource` entries and an asset root directory, reads each entry's real file from `asset_root / entry.path` and packs them into one self-describing binary blob: `u64 entry_count`, then that many `{u64 id; u64 offset; u64 size}` triples, then the concatenated data section. Throws `std::invalid_argument` if an entry's file can't be read — a build-time packaging step over trusted local input, matching the existing throw-on-malformed-input convention (distinct from `atlas::resource::ResourceRegistry`'s runtime return-value convention for the same class of failure at load time, since a missing asset *during a build* is an authoring error, not an ordinary runtime condition). Callers decide how entries are partitioned (typically one blob per asset type) — the function itself is agnostic to that and just packs whatever list it's handed. Integers are written host-native (`u64`); see `atlas-resource`'s README for why that's a stated, not silent, little-endian assumption.

- **`main.cpp` (the CLI)**, now `atlas-rcc <resource-manifest.yaml> <asset-root-dir> <output-dir>`: reads the manifest, calls `parse_resource_manifest` then `compile_resource_table`, prints the same summary as before (resource count, then one `id / type / name -> path` line per entry, `id` in hex), then partitions entries by `type` and calls `pack_resource_blob` once per type, writing each result to `<output-dir>/<type>.blob` (creating `output-dir` if needed) and printing one `packed N <type> resource(s) into '<path>' (<size> bytes)` line per blob written. Per-type entry lists are built directly from `parse_resource_manifest`'s authored-order `std::vector`, not by iterating the compiled `ResourceTable` (an `unordered_map`) — this keeps each blob's own byte layout bit-identical across repeated runs against the same manifest/assets (spec §4: avoid unordered iteration anywhere it could affect output), even though which type's blob gets written/printed first still isn't deterministic (harmless — it only affects console/write ordering, never a blob file's own contents). Matching `atlas-cgen`'s convention, `main.cpp` is excluded from the coverage gate (`cmake/CodeCoverage.cmake`'s existing `tools/[^/]+/src/main.cpp` glob already covers it without modification) — its argv/file-I/O error paths need subprocess-spawning test infrastructure this project doesn't build yet. The library logic it wires together (`parse_resource_manifest`, `compile_resource_table`, `pack_resource_blob`) is fully unit-tested in `tests/atlas-rcc/`; the CLI wiring itself was verified manually end-to-end (real manifest, real fixture assets, inspecting the written `.blob` bytes directly) rather than by an automated test, consistent with `main.cpp` being outside this project's unit-test/coverage boundary.

## Deliberately deferred (not corner-cutting — explicitly out of this round's scope)

- **No generated C++ header is emitted.** The issue's acceptance criteria treat the in-memory, fully-unit-tested `ResourceTable` as this round's real deliverable — proving the compile-time-identity mechanism (parse → validate → hash → table) — rather than also committing to a generated-file shape (constexpr array? `#include`-able table? one header per manifest, like `atlas-cgen`, or one aggregated table across a whole host's referenced resources?) before a real consumer exists to drive that design. `atlas-cgen`'s own template-embedding machinery (`cmake/scripts/EmbedTextFile.cmake`, `templates/*.tmpl`, `template_engine.hpp`) is the natural pattern to reuse once this is picked up — deliberately not duplicated speculatively here.
- **No integration into the build-time tooling pipeline yet.** The CLI now writes real `.blob` files given a manifest, asset root, and output directory (see "What's implemented" above), but nothing invokes it as part of an actual CMake build step yet — no `atlas_pack_resource_blobs`-style helper analogous to `atlas-cgen`'s `atlas_generate_capability_contract`. That wiring is a natural next step once a real consumer (a capability manifest's own resource references, or a host manifest's composed resource set) exists to drive it.
- **No project-wide/host-scoped resource registry.** Spec §3 describes a resource as "scoped to what the composing host actually references," implying resource compilation is eventually driven by a host's actual manifest-declared references, the same way `atlas-cgen`'s host composition mode resolves a `composes:` list against real capability manifests. This round compiles one manifest at a time, standalone — there is no equivalent of `atlas-cgen --host` yet.
- **`compile_resource_table`/`parse_resource_manifest` still do no path resolution or existence checking.** `path` stays an opaque authored string as far as those two functions are concerned; `pack_resource_blob` is what actually reads real files now, and only once a caller explicitly asks it to pack a given entry list — identity compilation itself remains untouched by that.
- **No hash-collision detection between distinct names.** `compile_resource_table` does not check whether two different (already-validated-as-non-duplicate) resource names happen to produce the same `atlas::ResourceId` (FNV-1a 64-bit) — astronomically unlikely at any realistic manifest size, and not exercisable by a real test case without deliberately searching for an FNV-1a collision pair, which felt like manufacturing a test rather than proving real behavior. Flagged here rather than silently assumed impossible.
- **No skeleton-reference validation (issue #45).** `compile_resource_table` resolves an `animation.skeleton` name to an `atlas::ResourceId` exactly like it resolves an entry's own `name`, but never checks that the resolved id actually corresponds to some other entry in the same manifest (or exists at all) — a dangling skeleton reference compiles without error. This mirrors this tool's existing stance on `path` (never checked against the filesystem): resolving a *name* to an *id* is a build-time, purely mechanical step; whether the referenced resource actually exists is a resolution-time concern for whatever host loads the compiled table at runtime.
- **`animation:` metadata never reaches `pack_resource_blob`/the binary blob format.** `pack_resource_blob` packs only the real asset file bytes behind `entry.path` — unchanged by this round, and deliberately so (see the issue's explicit scope boundary). `skeleton`/`loop`/`playback_rate` exist only in the in-memory `CompiledResource`/`ResourceTable`, the same "no generated header / no blob-embedded metadata yet" boundary this tool's other resolution data (`type`, `path`) already sits behind — see "No generated C++ header is emitted" above, which this extends rather than replaces.

## Real discoveries made building this

- **`FetchContent_Declare(yaml-cpp SYSTEM ...)` is duplicated from `tools/atlas-cgen/CMakeLists.txt` verbatim (same `GIT_TAG 0.8.0`), not shared via a common CMake include.** `FetchContent_Declare`/`_MakeAvailable` are idempotent per dependency name — declaring `yaml-cpp` a second time with identical arguments across two sibling `tools/` subdirectories does not re-download or conflict, confirmed by a clean `cmake --preset debug` configure with both tools present. This keeps `atlas-rcc` free of a build-ordering dependency on `atlas-cgen`'s own `CMakeLists.txt` existing or running first, matching this project's stated preference for tools/libraries with clear, independent dependency positions (§5).
- **A `type` field is open-ended vocabulary, unlike `atlas-cgen`'s closed field-type table.** `atlas-cgen` deliberately maps only a small, fixed set of manifest type tokens to C++ types (`map_field_type`) because it must know how to *emit* each one. `atlas-rcc`'s `type` is just downstream data carried through to whatever consumes the compiled table — there is no equivalent closed set to validate against here, and inventing one for this round would be exactly the "guessing at intent" this project's error-handling convention warns against.
- **Per-file branch coverage on `resource_table.cpp` reads low (`gcovr`'s per-file HTML report) even though the project-wide gate passes comfortably.** The `table.emplace(...)` call and the function's closing brace show partial/uncovered branch coverage — this is the same class of compiler-generated exception-unwind ("what if `std::string`/`unordered_map` allocation throws") edge `tools/atlas-cgen/README.md` already documents finding and excluding project-wide via `gcovr --exclude-throw-branches` (`cmake/CodeCoverage.cmake`), not a genuinely-unexercised code path — every line this file actually executes is covered, confirmed by its 100% line coverage.
- **Adding a fourth `ResourceEntry`/`CompiledResource` field surfaced every positional aggregate-init call site as a `-Wmissing-field-initializers` build failure.** `-Werror` treats a positional brace-init list that stops short of a struct's last member as an error (even though the trailing member has its own default), not just a warning to note and move past — every existing test literal building a `ResourceEntry` or `CompiledResource` by position (not just the new ones this round added) needed an explicit trailing `std::nullopt` once `animation` was added. Worth remembering for the *next* field added to either struct: this is a real, repository-wide compile break, not an isolated one-file fix.

## Dependency position

Depends on `yaml-cpp` (fetched, `SYSTEM`) for manifest parsing, and `atlas::resource` (for `atlas::ResourceId`/`ResourceId::from_name`) — the only `atlas-*` library dependency this tool needs, since it compiles *data* for that vocabulary type rather than generating C++ representations of vocabulary types the way `atlas-cgen` does. Does not depend on `atlas-cgen`, and `atlas-cgen` does not depend on this: per `tools/atlas-cgen/README.md`'s own "Contract generation vs. resource compilation" section, one emits contract *shape*, the other emits resource *data* — genuinely separate compile-time responsibilities (spec §12), not two modes of one tool.

## Open questions for a human reviewer

- **Generated-header shape.** Whichever future round adds file emission needs to settle: one header per manifest (mirroring `atlas-cgen`'s single-capability mode) vs. one aggregated table per host (mirroring `atlas-cgen`'s host composition mode) vs. both. This round's `ResourceTable` type is agnostic to that choice — it's an in-memory value, not tied to either shape yet.
- **`type` as a free-form string vs. a validated enum.** Left fully open-ended in this round (see "Real discoveries" above). If gameplay-facing tooling later wants compile-time or load-time confidence that `type` names a resource kind some consumer actually knows how to load, that validation would need its own closed vocabulary — deliberately not invented speculatively here.
- **Host-scoped compilation.** Spec §3's "scoped to what the composing host actually references" is not yet addressed at all — this round only ever compiles one manifest, standalone. Whether host-scoping becomes a second CLI mode (`atlas-rcc --host`, mirroring `atlas-cgen --host`) or a different mechanism entirely is left for whoever picks up the build-pipeline-integration follow-up.
- **CMake build-step wiring.** The CLI itself packs real blobs now, but no CMake helper invokes it as part of a build the way `atlas_generate_capability_contract` does for `atlas-cgen` — left for whoever picks up real build-pipeline integration (see "Deliberately deferred" above).
- **Blob filename collisions/sanitization.** `<type>.blob` is derived directly from the manifest-authored `type` string with no sanitization — a `type` containing path-hostile characters (e.g. a slash) would produce a surprising or invalid output path. Not guarded against this round, matching this tool's existing stance that `type` is open-ended, capability-authored vocabulary; worth a real fix once a manifest actually exercises this.
- **`animation.skeleton` resolution validation stayed out of scope by design (issue #45), same open question as host-scoped compilation above.** A dangling skeleton reference (a name with no corresponding entry, in this manifest or otherwise) compiles cleanly today — see "Deliberately deferred." Whether that ever becomes a build-time check (once host-scoped compilation exists and a manifest's full resource set is knowable in one place) or stays a purely load-time host concern is left open.
- **No fixture manifest YAML file was added under `tests/atlas-rcc/fixtures/`.** That directory holds only real binary asset bytes consumed by `pack_resource_blob`'s tests (`hero.mesh`, `hero.tex`) — every manifest-parsing test in `resource_manifest_test.cpp`, including this round's animation-block cases, uses an inline `constexpr std::string_view` YAML literal, matching that file's existing and only convention. Introducing a `.yaml` fixture file would have started a second, parallel convention for manifest tests specifically, so the animation-block coverage went into the existing inline-literal style instead of a new fixture file.
