# atlas-cgen

All Atlas platform tools are prefixed `atlas-` (library naming convention extended to tools), with the tool's C++ namespace matching the suffix (`atlas::cgen`, mirroring `atlas::core`).

**Status:** Implemented for the manifest shape spec §21's worked example uses, plus host composition (spec §14). Given a capability manifest YAML (`capability.name`, `depends_on`, `properties`, `requests`, `events`), emits the generated C++ contract header: one struct per property/request/event, with `static_assert(atlas::PropertyContract<T>)` / `RequestContract<T>` / `EventContract<T>` against the real concepts in `atlas-contracts`. Verified against the actual `health` capability from §21 two ways: a unit test asserting on the generated text (`tests/atlas-cgen/contract_writer_test.cpp`), and a build-time target (`tests/atlas-cgen/compile_check/`) that runs the real `atlas-cgen` binary against the fixture manifest and compiles the result against `atlas::contracts`/`atlas::entity` — a genuine compile-time proof, not a simulated one. A second fixture (`cosmetics`) proves the same for a `ResourceId`-typed field against `atlas::resource`. A third fixture (`armor`) proves the same for a property declaring an optional `composition:` key (spec §20, Property Composition): the property block may name a strategy (e.g. `composition: Additive`) alongside its ordinary fields, emitting a `static constexpr auto composition = atlas::Composition::Additive;` member plus an additional `static_assert(atlas::Composable<T>)` — matching §20's own generated-contract example exactly. A property with no `composition:` key (e.g. `Health`) is unaffected; `composition:` is recognized only while parsing the `properties:` block (it's a property-only concept per §20) — writing it under `requests:`/`events:` falls through to ordinary field parsing and is rejected as an unrecognized field type, an honest failure rather than silent, meaningless acceptance.

`atlas-contracts`'s own test suite (`tests/atlas-contracts/contract_concepts_test.cpp`) is wired to consume this generator's real output for the `health` fixture rather than a hand-copied stand-in struct — see `cmake/GenerateCapabilityContract.cmake`, the shared helper both test suites use to run `atlas-cgen` at build time against `tests/fixtures/*.capability.yaml`.

**Provides:** manifest validation, contract generation, dependency-graph resolution and cycle detection, host composition (spec §12's "Atlas Tooling").

**Spec:** [§12 Build Model](../../docs/specification/12-build-model.md), [§13 Library Architecture — Capability Manifest](../../docs/specification/13-library-architecture.md), [§14 Generated Contracts](../../docs/specification/14-generated-contracts.md), [§21 Worked Example](../../docs/specification/21-worked-example.md) (ground truth for the exact generated shape)

## Scope

Deliberately narrow, matching the project's established discipline of shipping one minimal real slice rather than the eventual full scope:

- **Parses:** `capability.name`, `depends_on` (carried through but not validated against a project-wide graph — see below), `consumes` (property names this capability reads but doesn't itself declare under `properties:` — carried through the same way, resolved only in host composition mode, see "Host composition" below), `properties`/`requests`/`events` (each a map of struct name → field name → type). Unknown top-level keys (`version`, `source`, `contracts`) are ignored, not rejected, for forward compatibility with real manifests (§13 shows these as required in practice; parsing them is a larger, separate task).
- **Type mapping** is a small, closed table (`int8`–`uint64`, `float`, `double`, `bool`, `EntityRef`, `ResourceId`) — anything else is a hard parse error, never guessed at. Widening it is a deliberate, reviewed decision. `EntityRef` and `ResourceId` are the two *vocabulary* types: each names its own required `#include` (`required_include_for_type` in `manifest.hpp`), collected and deduplicated across every field a manifest actually uses (`contract_writer.cpp`'s `collect_required_includes`) rather than one hard-coded "does this manifest use EntityRef" check. Whether a manifest field is *typed* as a resource identity is an ordinary structural fact this generator needs to emit — a different question from resource *compilation* (turning authored asset lists into compiled `ResourceId` tables), which is a separate future tool's job (see "Dependency position" below).
- **Does not emit** a `static_assert(atlas::DependsOn<...>)` line the way §21's illustrative pseudocode shows, in *single-capability* mode — a manifest generated on its own has no project-wide graph to validate `depends_on` against, and a hollow, always-true `DependsOn` concept would be worse than omitting it. Host composition mode (below) is where the graph and cycle detection this needs now actually live — see "Host composition."
- **Single-capability mode does not** validate `depends_on` against anything on its own, generate reflection/serialization metadata, or process `source`/`contracts` blocks.
- **Composition strategy mapping** (`map_composition_strategy` in `manifest.hpp`) is a small, closed table mirroring §20's Composition Strategies list exactly (`Additive`, `Multiplicative`, `Override`, `PriorityOverride`, `SetUnion`, `OrderedComposition`, `WeightedComposition`) — declared exhaustively even though `atlas-runtime`'s composition engine only has a working evaluator for `Additive` so far. A strategy name is part of a property's compile-time contract regardless of which strategies have an evaluator yet, the same reasoning `atlas::Composition` itself documents.
- **Wired into `atlas-contracts`'s test suite** (see above) as the first concrete rewiring; the library's own hand-written `contract_concepts.hpp` (the concepts themselves) stays hand-written — only the example *contract structs* used to test it are now generated. Rewiring an actual gameplay-facing library's contracts (as opposed to a test fixture) to be generated rather than hand-written remains a separate, larger follow-up.
- `main.cpp` (the CLI) is excluded from the coverage gate (`cmake/CodeCoverage.cmake`) — its argv/file-I/O error paths need subprocess-spawning test infrastructure this round doesn't build. The library logic it wires together (`parse_manifest`, `generate_contract`, `render_template`) is fully unit-tested.

## Host composition

A second, genuinely different generation mode alongside the single-capability one above (`atlas-cgen --host <host.yaml> <output.hpp> <capability.yaml>...`), matching spec §14's "one tool and one generation step, used uniformly for capability structure and host composition — not a separate mechanism for each":

- **`host_manifest.hpp`/`.cpp`** parses a host manifest (`host: GameplayClient` / `composes: [entity, health, ...]` — §14's own shape, verbatim) into a `HostManifest`. A missing `composes:` block parses as empty (not an error); a malformed or missing `host:` key is.
- **`dependency_graph.hpp`/`.cpp`** is the actual dependency graph and cycle detection spec §5 requires and single-manifest mode explicitly doesn't have: `resolve_composition_order` runs a deterministic depth-first topological sort over a plain `{name, depends_on}` node list, throwing `DependencyCycleError` — naming the *full* chain of edges forming the cycle, in order (e.g. `"dependency cycle: a -> b -> c -> a"`), per §5's explicit requirement, not just the first offending edge.
- **`property_graph.hpp`/`.cpp`** (`resolve_property_providers`, `resolve_property_dependency_edges`) resolves capability ordering from property flow instead of capability naming (issue #16: "systems coupled to data, not implementation" — the same principle §5's tiny-interface contracts already apply to entity/resource structure, extended to ordering itself). A manifest's `consumes:` list (a new, additive top-level field — see below) names properties, never capabilities; `resolve_property_providers` maps each property name declared under some composed manifest's `properties:` block to that manifest's own capability name, throwing `PropertyProviderConflictError` if two composed manifests declare the same property (exactly one provider per property, mirroring the design discussion's validation checklist — this is *not* the same concern as a property's `composition:` strategy, §20, which merges multiple *contributors'* values once a single provider already exists). `resolve_property_dependency_edges` then resolves every manifest's `consumes:` entries against that provider map into "consumer depends on provider" edges, throwing `UnresolvedPropertyConsumerError` if a consumed property has no provider among the composed set. `resolve_host_composition` merges these derived edges with each manifest's explicit `depends_on` edges before the graph goes through `resolve_composition_order` below — a property-driven cycle gets the exact same full-chain `DependencyCycleError` diagnostic as a `depends_on` cycle. `demo/modules/cast_time_attack/cast_time_attack.capability.yaml`'s `consumes: [CastSpeed]` (replacing a `depends_on: [haste]` entry) is the one worked example so far — every other capability's `depends_on` list is untouched, since several represent direct function calls between capabilities rather than property flow, and migrating those is a separate, larger increment.
- **`host_composition.hpp`/`.cpp`** (`resolve_host_composition`) resolves a `HostManifest` against every capability manifest a generation run was given: every name in `composes:` must resolve to a real manifest; every composed capability's own `depends_on` entries that name *another known capability* must themselves be composed too — composition here is always explicit, never an implicit transitive include (spec §4: no plugin discovery, nothing composed by magic). A `depends_on` entry with no corresponding manifest at all (e.g. `entity`, `resource` — a foundational runtime-library dependency, never itself a capability manifest in this generator's model) is silently treated as already satisfied. The composed subgraph (explicit `depends_on` edges plus `property_graph.hpp`'s derived edges) is then run through `resolve_composition_order` for real cycle detection and a real dependency order.
- **`host_composition_writer.hpp`/`.cpp`** (`generate_host_composition`) emits the actual generated header: a plain aggregate struct named after the host (Rule of Zero — no invariant, no hand-written constructor, matching every other generated contract struct), one `runtime::PropertyStore<T>` member per property declared by every composed capability (in dependency order), and one `inline void register_property_stores(Context&, Host&)` free function that registers each of them — the mechanical PropertyStore-registration boilerplate a hand-composed host previously had to spell out member-by-member (see `demo/tests/simulated_host.hpp`, now generated this way instead — replacing what used to be 11 hand-written `ctx.register_property_store(...)` calls with the host manifest `demo/tests/simulated_host.host.yaml` plus one generated function call).
- **Does not yet cover request-dispatch or event-subscription wiring.** A host's `ctx.subscribe<EventType>(...)` calls (e.g. `demo/tests/simulated_host.hpp`'s own wiring of `movement::PositionChanged` to `auto_attack`/`cast_time_attack`'s cancellation handlers) are still entirely hand-written. Covering that declaratively needs a new manifest field this generator doesn't have yet (something like a `subscribes:` block naming event → handler) and a corresponding spec addition — tracked as a distinct, deliberately separate follow-up (see the project's issue tracker), not attempted in this round.
- Proven against real code, not just generated text, via `tests/atlas-cgen/compile_check/host_composition_compile_check.cpp` (a fixture host composing `health`+`armor`, compiled for real against `atlas::runtime::PropertyStore`/`Context`) and, further, against `demo`'s own real `SimulatedHost` — a genuinely different level of proof than single-capability mode had before this: a mechanism this repo's own largest hand-composed host now actually depends on, not just a fixture.

## Templates

`templates/*.tmpl` are plain text files with `{{PLACEHOLDER}}` tokens — deliberately not a templating language (no loops or conditionals; see `template_engine.hpp`'s header comment). Repeated content (one struct per property/request/event) and conditional content (the `{{EXTRA_INCLUDES}}` block — zero, one, or both vocabulary-type `#include` lines) are assembled by ordinary C++ and handed in as single pre-built values. They're embedded into the binary at build time (`cmake/scripts/EmbedTextFile.cmake`, via `add_custom_command`) as `constexpr std::string_view` constants, so the generator never needs to locate template files on disk at runtime and editing a `.tmpl` file is an ordinary incremental-rebuild trigger.

## Real discoveries made building this (not hypothetical caveats)

- **`std::expected` doesn't work here.** This project's stated preference (`CLAUDE.md`) is `std::expected` for fallible operations, and that's how this tool was first written. It doesn't compile under Clang (18) + libstdc++ — libstdc++'s `<expected>` gates its entire contents behind `__cpp_concepts >= 202002L`, and Clang reports `201907L` (confirmed via `-dM -E`), so the header silently contributes nothing and `std::expected` is simply undeclared. Since this project's own CI explicitly builds with Clang against system libstdc++ (not libc++), this isn't a hypothetical — it's this exact toolchain. Rewritten to throw `std::invalid_argument` instead, consistent with how this code already interacts with `yaml-cpp`'s own exceptions. Nothing else in the repo used `std::expected` yet, so this is contained to `atlas-cgen`.
- **`FetchContent_Declare(... SYSTEM)`** (CMake ≥ 3.25) was required for `yaml-cpp`, not optional tidiness: without it, a `-Wshadow` warning inside `yaml-cpp`'s own headers (its enum members shadowing each other) still fails our `-Werror` via whichever of our files `#include`s it. `.clang-tidy`'s `HeaderFilterRegex` only suppresses clang-tidy's own *check* diagnostics for third-party headers, not the plain compiler diagnostics clang-tidy also surfaces. Applied to `googletest`'s `FetchContent_Declare` too for consistency, though no failure was observed there.
- **`gcovr --exclude-throw-branches` was required**, not just nice-to-have: this file's heavy `std::string` concatenation generates a large number of compiler-generated exception-unwind ("what if this throws `bad_alloc`") branch edges that are structurally untestable without fault injection. Before excluding them, every line gcov actually flagged as unexecuted was individually investigated and given a real test case (see `tests/atlas-cgen/*_test.cpp` — several tests exist specifically because this investigation found them, e.g. `RejectsNonMappingDocumentRoot`, `RejectsAFieldTypeMapFieldTypeDoesNotRecognize`). Only after confirming zero genuine gaps remained was the throw-branch exclusion added, project-wide, in `cmake/CodeCoverage.cmake`.
- **Raw string literal delimiters are capped at 16 characters** (a C++ standard limit) — `cmake/scripts/EmbedTextFile.cmake`'s first version used a 23-character delimiter and failed with a real, if slightly confusing, compiler error.

## Dependency position

Depends on `yaml-cpp` (fetched, `SYSTEM`) for manifest parsing. Does not depend on any other `atlas-*` library — `atlas::PropertyContract`, `atlas::runtime::PropertyStore`, etc. are referenced only as *emitted text*, not linked against. `tests/atlas-cgen/compile_check/` (not the library itself) links `atlas::contracts`, `atlas::entity`, `atlas::resource`, and (for the host-composition compile_check) `atlas::runtime` to prove generated output actually satisfies them.

## Contract generation vs. resource compilation

Spec §12 lists "contract generation" and "resource compilation" as two separate Atlas Tooling responsibilities — `atlas-cgen` is only the former. A manifest field typed `ResourceId` is, from this generator's point of view, exactly the same kind of fact as one typed `EntityRef`: a vocabulary type it knows how to map and `#include`. Turning an *authored asset list* (e.g. a capability's declared `ParticleEffects`/`MaterialLayers` resources) into the compiled `ResourceId` tables a running host resolves against is a different, not-yet-built tool's job — tentatively `atlas-rcc` ("resource compiler"), matching the `atlas-` tool-naming convention above. `atlas-cgen` will never need to depend on it, or vice versa: one emits contract *shape*, the other emits resource *data*.
