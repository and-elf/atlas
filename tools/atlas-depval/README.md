# atlas-depval

All Atlas platform tools are prefixed `atlas-` (library naming convention extended to tools), with the tool's C++ namespace matching the suffix (`atlas::depval`, mirroring `atlas::cgen`/`atlas::rcc`/`atlas::core`). Name chosen as short for "**dep**endency graph **val**idation" — the exact responsibility spec §12 (Atlas Tooling) lists as distinct from contract generation (`atlas-cgen`) and resource compilation (`atlas-rcc`): "capability dependency-graph validation (the cycle-detection compile-time failure required by §5)."

**Status:** Implemented, per issue #35. A standalone CLI + library that validates a composed host's capability dependency graph (spec §5, §13) and reports its full topological composition order — the same validation `atlas-cgen --host` already performs as one step of contract generation, exposed here as its own dedicated tool that only validates, and never emits generated code.

**Provides:** capability dependency-graph validation as a standalone build step — full-graph cycle detection with a full-chain diagnostic (spec §5: "the tooling must report the full chain of edges forming the cycle, not just the first one found"), and full topological composition-order resolution (spec §5, Ordering Without Stages: capability ordering — including ordering concerns that look like they need a separate stage/phase concept — is derived *entirely* from the graph).

**Spec:** [§5 Dependency Model](../../docs/specification/05-dependency-model.md) (the cycle-detection requirement and "Ordering Without Stages" this tool exists to enforce as its own step), [§12 Build Model](../../docs/specification/12-build-model.md) ("capability dependency-graph validation" listed as a distinct Atlas Tooling responsibility from contract generation and resource compilation), [§13 Library Architecture — Capability Manifest](../../docs/specification/13-library-architecture.md) (the `depends_on`/`consumes:` shape this tool validates)

## What this reuses from atlas-cgen vs. what this adds

`tools/atlas-cgen` already contains the real dependency-graph/cycle-detection engine, built and tested for its own host-composition generation mode: `dependency_graph.hpp`/`.cpp` (`resolve_composition_order`, full-chain `DependencyCycleError`), `property_graph.hpp`/`.cpp` (`consumes:`-derived edges, issue #16), and `host_composition.hpp`/`.cpp` (`resolve_host_composition`, which merges explicit `depends_on` edges with derived property edges before resolving them). None of that is reimplemented or copied here — `atlas-depval` links directly against `atlas-cgen`'s own linkable library target, `atlas::cgen_lib` (already exposed as its own CMake target, separate from the `atlas-cgen` executable, in `tools/atlas-cgen/CMakeLists.txt` — nothing needed to change there to make this possible), and calls `atlas::cgen::parse_host_manifest`, `atlas::cgen::parse_manifest`, and `atlas::cgen::resolve_host_composition` exactly as `atlas-cgen --host` mode's own `main.cpp` does.

What this tool adds, all of it new and unit-tested in `tests/atlas-depval/`:

- **`include/atlas/depval/validator.hpp` / `src/validator.cpp`** (`atlas::depval::validate_composition`) — a standalone-validator-shaped entry point around `resolve_host_composition`: takes a host manifest plus every composed capability manifest (as YAML text, not files — file I/O lives only in `main.cpp`), and returns a `ValidationReport` (host name + ordered capability names only). This is deliberately smaller than `atlas::cgen::HostComposition`, which carries a complete `atlas::cgen::Manifest` (properties/requests/events) per composed capability since it feeds contract-generation codegen — a concern this tool has no reason to carry. Every error `parse_host_manifest`/`parse_manifest`/`resolve_host_composition` can throw propagates unchanged, including `atlas::cgen::DependencyCycleError` with its full edge-chain message.
- **`atlas::depval::format_report`** — renders a `ValidationReport` as the human-readable text `atlas-depval` prints on success: the host name and one ordered line per composed capability, proving the *full* topological order is reported, not merely "no cycle found."
- **`src/main.cpp`** — a thin CLI: `atlas-depval <host.yaml> <capability.yaml>...` reads the files, calls `validate_composition`, and prints the rendered report on success or the propagated error's message to stderr (exit code 1) on failure — matching `atlas-cgen`'s and `atlas-rcc`'s own CLI conventions exactly. Unlike `atlas-cgen`, this tool takes no output path: it never generates a file, only validates and reports.
- **`tools/atlas-depval/CMakeLists.txt`** — a new linkable target (`atlas-depval-lib` / `atlas::depval_lib`) plus the `atlas-depval` executable, both linking `atlas::cgen_lib` directly rather than redeclaring `yaml-cpp` the way `atlas-rcc` does for its own, genuinely independent dependency (`atlas::resource`). This does introduce one real build-ordering requirement `atlas-rcc` doesn't have: `tools/CMakeLists.txt` must `add_subdirectory(atlas-cgen)` before `add_subdirectory(atlas-depval)`, since `target_link_libraries` needs `atlas-cgen-lib` to already exist as a target — documented at both the ordering site and the point of use.

## Scope

Deliberately narrow, matching this project's established discipline (see `tools/atlas-cgen/README.md`'s and `tools/atlas-rcc/README.md`'s own "Scope" sections) of shipping one minimal real slice:

- **Validates one host composition per invocation** — a host manifest (`host: GameplayClient` / `composes: [...]`, spec §14's shape) plus every capability manifest it composes, exactly matching `atlas-cgen --host`'s own input shape. There is no mode that validates a graph with no host at all (every capability manifest that exists, regardless of whether any host composes it) — a host's `composes:` list is what scopes which subgraph gets validated, per spec §3's "resource... scoped to what the composing host actually references" applied the same way to capability composition.
- **Cycle detection covers the full merged graph** — explicit `depends_on` edges plus `consumes:`-derived property edges (spec §5's cycle-detection requirement, extended by issue #16's property-graph edges) — never `depends_on` alone, since a cycle can just as easily be introduced purely through `consumes:` edges as through explicit ones.
- **Reports full topological order, not just cycle absence** — spec §5's "Ordering Without Stages" explicitly calls out that ordering concerns which look like they need a separate stage/phase concept (e.g. "presentation runs after simulation") fall out of the dependency graph alone; a tool that only answered "is there a cycle, yes/no" would leave that actual ordering unverified. `atlas-depval`'s output always includes the resolved order.
- **Does not generate any file.** Contract/host-composition code generation stays exactly where it already is, in `atlas-cgen`'s own generation modes (`atlas-cgen --host <host.yaml> <output.hpp> <capability.yaml>...`) — this tool is validation-only, matching its issue's literal scope ("Build capability dependency-graph validation tool," not "add a third `atlas-cgen` generation mode").
- **`main.cpp` (the CLI)** is excluded from the coverage gate (`cmake/CodeCoverage.cmake`'s existing `tools/[^/]+/src/main.cpp` glob already covers it without modification) — its argv/file-I/O error paths need subprocess-spawning test infrastructure this project doesn't build yet, the same reasoning `atlas-cgen`'s and `atlas-rcc`'s own READMEs give for their own `main.cpp`. The library logic it wires together (`validate_composition`, `format_report`) is fully unit-tested in `tests/atlas-depval/validator_test.cpp`, including a dedicated test asserting a three-capability cycle (`a -> b -> c -> a`) surfaces its *full* edge chain through this tool's own entry point, not just the first offending edge.

## Dependency position

Depends on `atlas::cgen_lib` only (which brings `yaml-cpp::yaml-cpp` transitively, since `atlas-cgen-lib` itself links it `PUBLIC`) — no other `atlas-*` library. Does not depend on `atlas-rcc`, and neither `atlas-cgen` nor `atlas-rcc` depends on this tool: `atlas-cgen` generates contract/host-composition code, `atlas-rcc` compiles resource data, and `atlas-depval` only validates a dependency graph as its own standalone step — three genuinely separate spec §12 Atlas Tooling responsibilities, not modes of one monolithic tool.
