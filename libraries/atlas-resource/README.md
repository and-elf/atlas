# atlas-resource

**Status:** Identity (`ResourceId`) plus a first real resolution slice (`ResourceRegistry`, issue #66). Implements `atlas::ResourceId` (`include/atlas/resource/resource_id.hpp`) — the resource-identity value type referenced as `atlas::ResourceId` by generated contracts (§21-style usage), the same convention as `atlas::EntityRef`. A `ResourceId` is derived from a stable, externally authored resource name (e.g. `"characters/hero/mesh"`) via a deterministic FNV-1a 64-bit hash (`ResourceId::from_name`), never from a filesystem path — the hash is a pure function of the name's bytes, so any two hosts computing it independently always agree, with no runtime discovery step (§4). The default-constructed / empty-name id is the null sentinel (`value == 0`, checked via `is_null()`), mirroring `EntityRef`'s null-index convention. A `std::hash<atlas::ResourceId>` specialization is provided so ids drop directly into `std::unordered_map`/`std::unordered_set` without extra boilerplate at resolver call sites. `from_name` is `constexpr` (issue #23) — a resource name known at compile time resolves to its id there too, usable in a `static_assert` or as a template non-type parameter, not only at runtime. Resource **management** (this library's third named responsibility, §13 — load/unload lifecycle, hot-reload) is still intentionally **not implemented** — see #67.

**Provides:** resource identity, resource resolution (first slice), resource management (not yet).

**Spec:** [§3 Architectural Definitions](../../docs/specification/03-architectural-definitions.md) (Resource: "an externally authored asset identified by a stable resource identity... resolved through generated metadata rather than hard-coded paths"), [§13 Library Architecture](../../docs/specification/13-library-architecture.md#library-responsibilities) (responsibility), [§5 Dependency Model](../../docs/specification/05-dependency-model.md) (dependency rules), [§6 Server Authority and Requests](../../docs/specification/06-server-authority-and-requests.md) (the uniform failure/event channel a resolution failure reports through), [§20 Property and Resource Composition](../../docs/specification/20-property-and-resource-composition.md) (resources compose the same way properties do; a resolved `ResourceId` is the kind of value a resource-typed property, e.g. `ParticleEffects: ResourceList`, would hold)

## What's implemented

- **`atlas::ResourceId`** (`include/atlas/resource/resource_id.hpp`) — identity only, described above.
- **`atlas::resource::ResourceEntry`, `ResourceRegistry`, `Resolution`/`ResolutionStatus`** (`include/atlas/resource/resource_registry.hpp`, `src/resource_registry.cpp`) — the first real resolution slice (issue #66):
  - `ResourceRegistry` is constructed from a `std::vector<ResourceEntry>` (`id`/`type`/`path`) plus a resource root directory (`std::filesystem::path`, always host-supplied — never hard-coded, §3), and partitions entries by `type` exactly once, at construction. `resolve(type_name, id)` does a partition lookup followed by an id lookup — it never re-inspects a resource's `type` per call, and a caller resolving its own asset kind (`atlas-render` asking for `"Mesh"`, `atlas-audio` asking for `"Sound"`) never runs a branch over `type` at its own call site either.
  - `resolve()` returns one of three `ResolutionStatus` values, closing #63's open question: `Unresolved` (id absent from the registry, or a null id — matches `atlas-render`'s existing "null means skip" convention), `Resolved` (file read successfully; `Resolution::bytes` holds the raw content), or `ResolutionFailed` (present in the registry, but the file couldn't be read). This is a return value, not a thrown exception — a missing asset at runtime is an ordinary condition a host observes through §6's uniform failure/event channel, distinct from the parse-time `std::invalid_argument`s `atlas-cgen`/`atlas-rcc` throw for malformed *input*.
  - Reads raw bytes only — no mesh/material/audio format decoding. That stays downstream, in `atlas-render`'s (#69) and `atlas-audio`'s (#55) own follow-ups.

## Scoping decisions

**`ResourceEntry` is deliberately independent of `atlas::rcc::CompiledResource`.** `atlas-rcc` (#33) already depends on `atlas::resource` for `ResourceId` — `atlas-resource` depending back on `atlas-rcc`'s compiled-table type would be a dependency cycle (§5), a hard compile-time failure this project's own tooling is meant to catch, not something either library should informally step around. A composing host converts `atlas-rcc`'s `ResourceTable` into a `std::vector<ResourceEntry>` itself; the two libraries never reference each other's types.

**One manifest's compiled table at a time, not host-scoped yet.** `atlas-rcc` has no generated-header emission (its own README lists this as open) and no host-scoped aggregation across a host's full composed reference set either. Rather than block on either, this round has the composing host call `atlas-rcc`'s `parse_resource_manifest`/`compile_resource_table` directly and convert the result — host-scoped aggregation stays open, mirroring `atlas-rcc`'s own "host-scoped compilation" open question.

**Real filesystem I/O here is not a §4 determinism violation.** Resource loading sits outside the bit-exact simulation boundary the same way rendering and audio already do (§19 states this explicitly for those two) — nothing in `resolve()`'s result feeds back into simulation state.

## Dependency position

`atlas-resource` depends on `atlas_project_options`/`atlas_project_warnings` and the standard library (`<filesystem>`, `<fstream>`) — still no dependency on `atlas-core` or `atlas-entity`, and deliberately none on `atlas-rcc` (see Scoping above). Per §5, it may depend on lower-level libraries and generated contracts as those needs arise, never upward on capabilities, applications, editor/deployment-specific code, or on `atlas-rcc` (a tool built on top of it).

**No longer header-only.** `ResourceId::from_name` is still `constexpr` and `resource_id.hpp` stays header-only itself, but `ResourceRegistry`'s real file I/O needs a `.cpp`, so the library as a whole is a regular compiled target again (`atlas_project_options` `PUBLIC`, `atlas_project_warnings` `PRIVATE`, matching the `atlas-core` pattern) rather than the `INTERFACE` library it was when `ResourceId` was its only content.

## Open questions (flagging for human review, not silently resolved)

- **Host-scoped compilation** — see Scoping above; unaddressed this round, same as `atlas-rcc`'s own open question.
- **Typed-view caching.** `resolve()` takes `type_name` on every call rather than a capability pre-fetching a cached view of just its own partition once at composition time. Left simple deliberately — introducing a caching view type before a real caller (`atlas-render`/`atlas-audio`) exists to demand it would be designing for a hypothetical requirement rather than a real one.
- **Resource management** (hot-reload, load/unload lifecycle) — tracked separately, #67.
