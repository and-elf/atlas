# atlas-resource

**Status:** Identity (`ResourceId`), a first real resolution slice (`ResourceRegistry`, issue #66), plus development-only hot-reload (issue #67). Implements `atlas::ResourceId` (`include/atlas/resource/resource_id.hpp`) — the resource-identity value type referenced as `atlas::ResourceId` by generated contracts (§21-style usage), the same convention as `atlas::EntityRef`. A `ResourceId` is derived from a stable, externally authored resource name (e.g. `"characters/hero/mesh"`) via a deterministic FNV-1a 64-bit hash (`ResourceId::from_name`), never from a filesystem path — the hash is a pure function of the name's bytes, so any two hosts computing it independently always agree, with no runtime discovery step (§4). The default-constructed / empty-name id is the null sentinel (`value == 0`, checked via `is_null()`), mirroring `EntityRef`'s null-index convention. A `std::hash<atlas::ResourceId>` specialization is provided so ids drop directly into `std::unordered_map`/`std::unordered_set` without extra boilerplate at resolver call sites. `from_name` is `constexpr` (issue #23) — a resource name known at compile time resolves to its id there too, usable in a `static_assert` or as a template non-type parameter, not only at runtime. Resource **management** (this library's third named responsibility, §13 — load/unload lifecycle) now has its first slice too: `ResourceRegistry::poll_for_changes()` detects a changed blob file and reloads it in place, opt-in and dev/editor-host-scoped (see "What's implemented" below).

**Provides:** resource identity, resource resolution (first slice), resource management (hot-reload, first slice).

**Spec:** [§3 Architectural Definitions](../../docs/specification/03-architectural-definitions.md) (Resource: "an externally authored asset identified by a stable resource identity... resolved through generated metadata rather than hard-coded paths"), [§13 Library Architecture](../../docs/specification/13-library-architecture.md#library-responsibilities) (responsibility), [§5 Dependency Model](../../docs/specification/05-dependency-model.md) (dependency rules), [§6 Server Authority and Requests](../../docs/specification/06-server-authority-and-requests.md) (the uniform failure/event channel a resolution failure reports through), [§20 Property and Resource Composition](../../docs/specification/20-property-and-resource-composition.md) (resources compose the same way properties do; a resolved `ResourceId` is the kind of value a resource-typed property, e.g. `ParticleEffects: ResourceList`, would hold)

## What's implemented

- **`atlas::ResourceId`** (`include/atlas/resource/resource_id.hpp`) — identity only, described above.
- **`atlas::resource::ResourceRegistry`, `Resolution`/`ResolutionStatus`** (`include/atlas/resource/resource_registry.hpp`, `src/resource_registry.cpp`) — the first real resolution slice (issue #66), resolving against packed, in-memory blobs rather than loose files on disk:
  - `ResourceRegistry` is constructed from a `type name → blob file path` mapping. Every blob is read fully into memory exactly once, here at construction — `resolve(type_name, id)` afterward never touches the filesystem at all, only an in-memory index lookup plus a byte-range copy out of an already-resident buffer. A caller resolving its own asset kind (`atlas-render` asking for `"Mesh"`, `atlas-audio` asking for `"Sound"`) never runs a branch over a resource's `type` at its own call site, and never pays a per-load filesystem cost after startup.
  - Each blob is the self-describing binary format packed by `atlas::rcc::pack_resource_blob` (`tools/atlas-rcc/include/atlas/rcc/resource_blob.hpp`): `u64 entry_count`, then that many `{u64 id; u64 offset; u64 size}` triples, then the concatenated data section. `ResourceRegistry` independently re-implements a reader against this same documented layout rather than depending on `atlas-rcc`'s header — see Scoping below for why.
- **`ResourceRegistry::poll_for_changes()`, `ResourceChangeEvent`/`ResourceChangeKind`** (issue #67) — development/editor-only hot-reload, opt-in purely by whether a caller ever invokes this method: a headless production host that never calls `poll_for_changes()` pays nothing beyond the `std::filesystem::last_write_time` query already done once per registered type at construction. Checks every registered type's blob file's last-write-time; a type whose write time differs from what was last observed is reloaded immediately via the same `load_blob()` construction uses, replacing its stale `LoadedBlob` in place so a subsequent `resolve()` call returns fresh bytes — `resolve()` itself never reloads anything, staying a pure in-memory lookup exactly as before. No background thread, no signal handler — nothing happens except when the caller explicitly polls, mirroring `atlas::replication::Transport::poll_received()`'s and `PhysicsBackend::poll_contact_events()`'s existing "batch of events accumulated since last check, drained per call" precedent. Reload failure (blob now missing, or malformed the same way the constructor already handles) is reported as `ResourceChangeKind::ReloadFailed`, not an exception, matching `load_blob()`'s own return-value convention; a subsequent `resolve()` call for that type then reports `ResolutionStatus::ResolutionFailed` exactly as it would for a blob that failed to load at construction. The returned `std::span` aliases the registry's own internal buffer, valid until the next `poll_for_changes()` call — overwritten, not appended to, each call. Events are sorted by `type_name` so the return order is deterministic regardless of the backing `unordered_map`'s own iteration order (§4: avoid unordered iteration anywhere it could affect output).
  - `resolve()` returns one of three `ResolutionStatus` values, closing #63's open question: `Unresolved` (type never registered, or the type's loaded blob doesn't contain this id, or a null id — matches `atlas-render`'s existing "null means skip" convention), `Resolved` (the type's blob loaded successfully and contains this id; `Resolution::bytes` holds a copy of its data), or `ResolutionFailed` (the type was registered, but its blob failed to load or was malformed — truncated header, truncated index, or an index entry pointing past the data section are all treated as malformed, not read out of bounds). This is a return value, not a thrown exception — a missing/corrupt blob at runtime is an ordinary condition a host observes through §6's uniform failure/event channel, distinct from the parse-time `std::invalid_argument`s `atlas-cgen`/`atlas-rcc`/`pack_resource_blob` throw for malformed *input* to a build-time step.
  - Reads raw bytes only — no mesh/material/audio format decoding. That stays downstream, in `atlas-render`'s (#69) and `atlas-audio`'s (#55) own follow-ups.

## Scoping decisions

**Packed blobs, not loose files — and not literal binary embedding either.** An earlier round of this issue resolved directly against one loose file per resource, one `open()`/`read()` per `resolve()` call — the wrong shape for a real load path (many small files, many syscalls, no locality) and for deployment (no atomic patching of individual files). The alternative of embedding asset bytes into the compiled binary (Qt `rcc`-style) was considered and rejected: compiling multi-megabyte assets as generated C++ byte arrays blows up build times and loses independent patchability, and doesn't even buy a runtime win — a fully-resident, once-loaded external blob behaves identically to embedded data once resident, since the OS's page cache already treats both the same way. Packed blobs loaded fully into memory once, at construction, get the real win (no filesystem access on the hot path) without either cost.

**The blob format is documented and independently implemented on each side, not a shared dependency.** `atlas-rcc` (#33) already depends on `atlas::resource` for `ResourceId` — `atlas-resource` depending back on `atlas-rcc`'s writer would be a dependency cycle (§5), a hard compile-time failure this project's own tooling is meant to catch. Matches this repo's existing precedent of duplicating a small, stable piece of logic independently across two call sites rather than introducing coupling for it (`ResourceId`'s own FNV-1a implementation is similarly duplicated, not shared, in `atlas::PropertyId`).

**Integers in the blob format are host-native (`u64`), little-endian in practice.** Stated explicitly rather than silently assumed: all three deployment targets (Debian 13 x86-64, macOS ARM, Windows x86-64) are little-endian, so no explicit endianness handling is implemented.

**One manifest's compiled table at a time, not host-scoped yet.** `atlas-rcc` has no generated-header emission (its own README lists this as open) and no host-scoped aggregation across a host's full composed reference set either. Rather than block on either, this round has the composing host call `atlas-rcc`'s `parse_resource_manifest`/`compile_resource_table`/`pack_resource_blob` directly — host-scoped aggregation stays open, mirroring `atlas-rcc`'s own "host-scoped compilation" open question.

**Real filesystem I/O here is not a §4 determinism violation.** Resource loading sits outside the bit-exact simulation boundary the same way rendering and audio already do (§19 states this explicitly for those two) — nothing in `resolve()`'s result feeds back into simulation state.

## Dependency position

`atlas-resource` depends on `atlas_project_options`/`atlas_project_warnings` and the standard library (`<filesystem>`, `<fstream>`) — still no dependency on `atlas-core` or `atlas-entity`, and deliberately none on `atlas-rcc` (see Scoping above). Per §5, it may depend on lower-level libraries and generated contracts as those needs arise, never upward on capabilities, applications, editor/deployment-specific code, or on `atlas-rcc` (a tool built on top of it).

**No longer header-only.** `ResourceId::from_name` is still `constexpr` and `resource_id.hpp` stays header-only itself, but `ResourceRegistry`'s real file I/O needs a `.cpp`, so the library as a whole is a regular compiled target again (`atlas_project_options` `PUBLIC`, `atlas_project_warnings` `PRIVATE`, matching the `atlas-core` pattern) rather than the `INTERFACE` library it was when `ResourceId` was its only content.

## Open questions (flagging for human review, not silently resolved)

- **Full in-RAM load vs. memory-mapping.** Every blob's entire contents load into a `std::vector<std::byte>` at construction. For very large asset sets this could mean a large resident footprint even for content never actually queried. A memory-mapped alternative (`mmap`/`MapViewOfFile`) would let the OS page content in on demand instead — not attempted yet since C++ has no standard cross-platform memory-mapped-file facility, and reaching for one would mean either platform-conditional code or a new third-party dependency, neither justified without a real caller hitting a real memory ceiling first.
- **Host-scoped compilation** — see Scoping above; unaddressed this round, same as `atlas-rcc`'s own open question.
- **Typed-view caching.** `resolve()` takes `type_name` on every call rather than a capability pre-fetching a cached view of just its own partition once at composition time. Left simple deliberately — introducing a caching view type before a real caller (`atlas-render`/`atlas-audio`) exists to demand it would be designing for a hypothetical requirement rather than a real one.
- **No CLI wiring.** Nothing yet writes `.blob` files to disk from a manifest as part of a build step — `pack_resource_blob`/`ResourceRegistry` are this round's real (fully tested) library-level deliverable, matching how `atlas-rcc`'s own original round deferred build-pipeline integration for the same reason.
- **Hot-reload consumer wiring.** `poll_for_changes()` reports which *types* changed; nothing yet calls it on a timer/tick or notifies a downstream consumer (`atlas-render`'s upload caches, `atlas-audio`) that its own previously-resolved `Resolution` is now stale beyond "the next `resolve()` call happens to return different bytes." That integration is left for whichever of those libraries' own follow-up issues picks it up.
- **Load/unload lifecycle** (evicting a type's blob entirely, not just reloading it in place) remains unaddressed — `poll_for_changes()` only ever replaces an already-registered type's blob, never adds or removes a type from `blobs_by_type_`.
