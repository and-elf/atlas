# atlas-scheduler

**Status:** Seeded. Implements `atlas::scheduler::Scheduler` (`include/atlas/scheduler/scheduler.hpp`), which consumes an already-built `atlas::stage::StageSequence` and lets callers `schedule()` a `Job` (`std::function<void()>`) against a specific `atlas::stage::StageId`. `run_tick()` runs every registered job exactly once: stage by stage in the sequence's fixed order, and within a stage in the exact order the jobs were registered — never an unordered container, consistent with the "fixed, reproducible stage and job order" determinism guarantee (§4).

`Scheduler` also implements an opt-in parallel execution mode: `schedule_parallel()` registers a `ParallelJob` (`std::function<Apply()>`, where `Apply` is `std::function<void()>`) against a stage, and `run_tick_parallel()` runs a stage's `ParallelJob`s concurrently — one real OS thread per job (`std::async(std::launch::async, ...)`) — then applies every job's returned `Apply` closure serially, strictly in registration order, only after every job in that stage has finished. Stages themselves still run one at a time, in the sequence's fixed order; only the jobs *within* a stage run concurrently. This is a separate, independent job list from `schedule()`/`run_tick()` — the plain sequential path is untouched by this addition. Nothing else in this library's eventual scope (per-job dependency edges finer than stage granularity, job cancellation, a persistent/reusable thread pool instead of per-tick `std::async` launches, etc.) is implemented yet.

This is the piece §5 (Ordering Without Stages) points at as the runtime-internal mechanism that actually walks the fixed sequence every tick: `atlas-stage` supplies the fixed order (a `StageSequence`), `atlas-scheduler` is what registers work against it and executes that work in that order.

**Scoping decisions:**
- `Job` is a plain `std::function<void()>` with no context parameter. The typed, monadic context API (`ctx.get<T>()`, `ctx.publish<T>()`, §21) belongs to the not-yet-built capability/contract/runtime layer; this library only needs "something callable," not a capability-shaped signature, to prove out fixed-order execution.
- `Scheduler::schedule` returns `false`, and leaves the scheduler unmodified, when asked to register a job against a `StageId` that is not part of the sequence the scheduler was constructed with — mirroring `atlas::stage::StageSequence::create` (duplicate stage) and `atlas::entity::EntityRegistry::destroy` (stale/unknown ref) rejecting invalid input outright rather than silently dropping it, coercing it, or throwing.
- `run_tick()` does not consume or clear registered jobs. Registering a job models composing a persistent unit of work into a stage (closer to registering a system than enqueuing a one-shot task), so a `Scheduler` is expected to be built once and have `run_tick()` invoked repeatedly — once per host tick — for as long as the host runs, always producing the same job order on every call.
- Job storage is `std::vector<std::pair<StageId, std::vector<Job>>>`, one entry per stage in the sequence's order, populated once at construction and looked up by linear scan in `schedule()`. This is a deliberate rejection of any hash-based container for the lookup: with only as many entries as there are stages, and lookups only happening at registration time (never inside `run_tick()`'s hot path), a linear scan costs nothing that matters and keeps every ordering-relevant part of this type free of hash-derived iteration order, per §4.
- `run_tick()` remains intentionally single-threaded and strictly sequential — no form of parallelism was retrofitted onto it.
- `run_tick_parallel()` (issue #78) is the scoped, additive answer to §4's "unordered iteration over concurrent or parallel work" constraint: it proves real thread-based parallelism is possible within a stage *without* giving up the fixed, reproducible merge order §4 requires for anything that writes back into shared/simulation state.
  - `ParallelJob` splits into two phases on purpose: a concurrent computation phase (the job body, run on its own thread) and a serial merge phase (the returned `Apply` closure, invoked later in registration order). A `ParallelJob` must not touch state shared with any other job registered against the same stage during its concurrent phase — only through the `Apply` closure it returns, after the barrier. This mirrors §20 (Property Composition): concurrent capabilities never reach into shared state directly, they only contribute through a defined merge mechanism.
  - The barrier between phases is a plain "collect every future, then apply every result" loop: every job in a stage is launched before any of their `Apply` closures are read, so the order results are *applied* in depends only on registration order, never on which thread happened to finish its sleep/computation first. `tests/atlas-scheduler/scheduler_test.cpp` proves this directly by injecting randomized sleep jitter into each job and asserting bit-exact, identical output across many repeated runs — the same category of test `atlas-core::Random`'s determinism tests use for its seeded stream.
  - `std::async(std::launch::async, ...)` (one real thread per job, not a shared/reusable pool) was chosen over hand-rolling a persistent thread pool: at this library's current job counts (per-stage, per-tick), a fresh thread per job is simple, correct, and easy to reason about, and a reusable worker pool is a valid future optimization that doesn't change the merge-order guarantee this issue is scoped to. `RunTickParallelActuallyUsesMultipleThreads` (in the test suite) asserts more than one distinct thread ID is actually observed, so this isn't a sequential implementation disguised as parallel.
  - An empty (default-constructed) `Apply` returned by a `ParallelJob` is treated as "no write-back" and skipped rather than invoked — calling a default-constructed `std::function` would throw `std::bad_function_call`, and a job with nothing to merge back is a legitimate case (e.g. a job that only performs a read-only check).

## Dependency position

`atlas-scheduler` depends on `atlas::stage` (public: `Scheduler`'s constructor and `schedule()` take `atlas::stage` types directly in its public interface) plus `atlas_project_options`/`atlas_project_warnings`, the platform threading library (`Threads::Threads`, needed by `run_tick_parallel()`'s use of `std::async`/`std::future`), and the standard library. Per §5, it may depend on further lower-level libraries and generated contracts as those needs arise, never upward on capabilities, applications, or editor/deployment-specific code.
