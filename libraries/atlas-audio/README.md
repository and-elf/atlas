# atlas-audio

**Status:** Seeded (issue #31). Implements `atlas::audio::render()` and `atlas::audio::ResolvedCue` (`include/atlas/audio/sound_renderer.hpp`) — the audio renderer's "renderer" step in spec §19's shared `State → Renderer → Output` pattern ("this is the same pattern as the 3D and audio renderers: game state flows into a renderer, which produces output"). `render()` consumes a tick's already-composed per-voice state (a `ResourceId` cue reference, an effective gain, an effective pan — each stored in a real `atlas::runtime::PropertyStore<T>`, keyed by the `atlas::EntityRef` "voice" they belong to) and produces a deterministically ordered list of `ResolvedCue` entries: which entity is playing which cue, at what clamped gain and pan. No new third-party dependency was added to build this — no miniaudio/SDL/platform audio API — see "Scoping: no device I/O this round" below for why that's a deliberate decision, not an oversight.

**Provides:** audio rendering — consumes composed properties and resources (game state), produces sound output; no gameplay semantics (§24, Non-Goals).

**Spec:** [§13 Library Architecture](../../docs/specification/13-library-architecture.md#library-responsibilities) (responsibility; optional library, alongside `atlas-render`/`atlas-ui`), [§19 UI System](../../docs/specification/19-ui-system.md) (the `State → Renderer → Output` pattern shared by the 3D/audio/UI renderers — the design this library follows even though §19 itself is about the UI renderer specifically), [§24 Non-Goals](../../docs/specification/24-non-goals.md) (mechanism-not-meaning: this library renders composed audio state, it never defines what a cue *sounds like* or *means* — sound design/content authoring stays an application concern), [§20 Property and Resource Composition](../../docs/specification/20-property-and-resource-composition.md) (gain/pan are ordinary composed properties; resources — the sound-cue reference itself — compose the same way, §20: "Resources... compose the same way properties do, same mechanism, not a special case"), [§4 Architectural Invariants](../../docs/specification/04-architectural-invariants.md) (determinism constraints this library's design follows throughout)

## What this round implements

- `atlas::audio::ResolvedCue` — a plain aggregate (rule of zero: no invariant beyond its four fields) reporting one voice's resolved, mix-ready state: `source` (`EntityRef`), `cue` (`ResourceId`), `effective_gain`, `effective_pan`.
- `atlas::audio::render(voices, cues, gains, pans)` — the mixer/composition function the issue asks for. It walks `voices` (a caller-supplied, explicitly ordered `std::span<const EntityRef>`) and, for each entity, looks up its composed cue/gain/pan from three real `atlas::runtime::PropertyStore<T>` instances (the same storage type `atlas::Context::get<T>()` reads through elsewhere in the runtime, per `atlas-runtime`'s own README). A voice missing *any* of the three properties this tick is skipped entirely — "not fully composed yet" is treated as "not currently audible," never defaulted or guessed at. Present voices have their gain clamped to `[0, 1]` and pan clamped to `[-1, 1]` (`clamp_gain`/`clamp_pan`, both `constexpr`) before being reported.
- The function never iterates a `PropertyStore` directly (each one is backed by `std::unordered_map`, whose iteration order isn't part of its contract) — it only ever looks entities up by the order the caller already fixed via `voices`, satisfying spec §4's "avoid unordered iteration... anywhere it could affect output" directly rather than by convention.
- `render()` reads no wall-clock time, no platform entropy, and no global/static state of any kind — it is a pure function of its four arguments. Given identical `PropertyStore` contents and an identical `voices` order, it returns bit-identical output on every call; `tests/atlas-audio/sound_renderer_test.cpp`'s `Render.RepeatedCallsWithIdenticalInputsProduceBitIdenticalOutput` asserts exactly that, matching this codebase's existing convention (per CLAUDE.md, `atlas-core`'s `Random`) of treating bit-exact repeatability as a real, checkable test category rather than an assumption.
- `Render.ConsumesGainComposedThroughTheRealPropertyCompositionEngine` (same test file) exercises the intended end-to-end pipeline explicitly: a gain value produced by `atlas::runtime::resolve_multiplicative` over real `atlas::runtime::Contribution<float>` values is stored into a `PropertyStore<float>` and only then handed to `render()` — proving this library integrates with `atlas-runtime`'s actual composition machinery rather than a hand-rolled stand-in for it.

## Scoping: no device I/O, no sample synthesis, this round

Issue #31 explicitly scopes this pass to a "minimal TDD scaffold" and defers real audio device I/O to a follow-up issue — **no new third-party dependency (miniaudio, SDL, a platform audio API) was added**, and nothing in this library opens an audio device, decodes an audio file, or produces actual audible sound. That deferral is stated here plainly rather than silently absorbed into "implemented."

A second, related scoping decision this round made explicitly (the issue's own wording: *"your call, but make the reasoning explicit"*): **the "sound output" this library produces is the resolved-entries list described above, not a raw numeric sample buffer.** Two concrete reasons, not just "the lighter option was easier":

1. **There is no audio content to synthesize from yet.** A `ResourceId` is a stable identity, nothing more — `atlas-resource`'s own README states plainly that resource *resolution* (turning an id into the actual authored asset behind it) isn't built yet, only identity is. Producing a real sample buffer requires decoded PCM data to mix; without a resolver, the only way to get *something* into a buffer would be inventing a placeholder waveform (e.g. a synthetic tone keyed off the `ResourceId`'s hash). That would mean this library manufacturing audio content out of nothing meaningful — which is exactly the "sound design" territory §24 keeps on the application side of the mechanism/meaning boundary, not a platform mechanism.
2. **The resolved-entries list is the direct analogue of what the sibling renderers in §19 already produce at this layer.** §19 describes the UI renderer's compositing layers as "producing draw calls rather than texture layers" — an intermediate, mixer-ready representation, not final pixels. `ResolvedCue` is that same shape for audio: a resolved, ready-to-mix description of what should be audible and how, deferring the actual DSP/PCM step to whatever real device-backed mixer a follow-up issue builds.

Once resource resolution exists (a real `atlas-resource` follow-up) and a device I/O layer is chosen (the issue's stated next issue), the natural extension is a second function consuming `std::span<const ResolvedCue>` plus decoded per-cue PCM data and producing an actual sample buffer — `render()`'s output shape was chosen specifically so that extension slots in without changing anything upstream of it.

## Dependency position

`atlas-audio` depends publicly on `atlas::runtime` (for `PropertyStore<T>`, and transitively `atlas::entity` for `EntityRef`) and `atlas::resource` (for `ResourceId`), plus `atlas_project_options`/`atlas_project_warnings` and the standard library — following the `atlas-core` CMake pattern exactly (`atlas_project_options` PUBLIC, `atlas_project_warnings` PRIVATE). Per §5 and §13, this is an **optional** library: a headless server host must never gain a dependency on `atlas-audio`, and nothing in `libraries/atlas-runtime`, `libraries/atlas-entity`, or any other non-optional library depends on it in the other direction. `atlas-audio` itself depends only downward (on runtime libraries and generated contracts), never on `atlas-render`, `atlas-ui`, `atlas-input`, or `atlas-editor` — each of those is a sibling optional library, not a dependency of this one.

## Open questions (flagging for human review, not silently resolved)

- **Gain/pan composition strategy.** This round treats gain and pan as ordinary composed `float` properties the caller resolves upstream (e.g. via `resolve_multiplicative` for gain, as the integration test demonstrates) before ever reaching `render()`. Spec §20 doesn't pin down which of the seven composition strategies is "correct" for pan specifically — Additive (a plausible fit, since multiple simultaneous stereo-position nudges would sum) is assumed by the integration test's shape but never enforced by this library, since `render()` accepts an already-resolved value and has no opinion on how it got there. Whoever writes the first real audio-emitting capability should confirm Additive is actually the right choice for pan before relying on it.
- **Gain ceiling of exactly 1.0.** `clamp_gain` hard-codes `[0, 1]` (unity gain as the ceiling). A capability wanting deliberately "louder than normal" emphasis (e.g. a boss-cue mix override) would need a different mechanism (a second, uncapped gain-multiplier stage downstream of this one) rather than this function's ceiling being configurable — left as a future decision rather than guessed at now, since nothing in this round's scope needs it.
- **One cue per voice, this round.** `render()`'s three `PropertyStore`s model exactly one active cue per entity. A capability wanting an entity to emit several simultaneous cues (e.g. footsteps *and* a voice line at once) would need multiple voice `EntityRef`s (one per concurrent cue), which works today but wasn't the scenario driving this round's test suite — flagging in case a reviewer wants a richer per-entity multi-voice shape instead.
- **Real sample synthesis and device I/O** — see "Scoping" above; both are explicitly deferred to a follow-up issue, not attempted here.
