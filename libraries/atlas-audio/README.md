# atlas-audio

**Status:** Seeded (issue #31); real SDL3 device I/O backend added (issue #55). Implements `atlas::audio::render()` and `atlas::audio::ResolvedCue` (`include/atlas/audio/sound_renderer.hpp`) — the audio renderer's "renderer" step in spec §19's shared `State → Renderer → Output` pattern ("this is the same pattern as the 3D and audio renderers: game state flows into a renderer, which produces output"). `render()` consumes a tick's already-composed per-voice state (a `ResourceId` cue reference, an effective gain, an effective pan — each stored in a real `atlas::runtime::PropertyStore<T>`, keyed by the `atlas::EntityRef` "voice" they belong to) and produces a deterministically ordered list of `ResolvedCue` entries: which entity is playing which cue, at what clamped gain and pan. `Sdl3AudioBackend` (issue #55, see its own section below) now turns that resolved-entries list into real audible output via SDL3's `SDL_AudioStream` API — see "Sdl3AudioBackend: real SDL3 device I/O" below for what changed and why, and "Scoping" further down for what is still deliberately not attempted.

**Provides:** audio rendering — consumes composed properties and resources (game state), produces sound output; no gameplay semantics (§24, Non-Goals).

**Spec:** [§13 Library Architecture](../../docs/specification/13-library-architecture.md#library-responsibilities) (responsibility; optional library, alongside `atlas-render`/`atlas-ui`), [§19 UI System](../../docs/specification/19-ui-system.md) (the `State → Renderer → Output` pattern shared by the 3D/audio/UI renderers — the design this library follows even though §19 itself is about the UI renderer specifically), [§24 Non-Goals](../../docs/specification/24-non-goals.md) (mechanism-not-meaning: this library renders composed audio state, it never defines what a cue *sounds like* or *means* — sound design/content authoring stays an application concern), [§20 Property and Resource Composition](../../docs/specification/20-property-and-resource-composition.md) (gain/pan are ordinary composed properties; resources — the sound-cue reference itself — compose the same way, §20: "Resources... compose the same way properties do, same mechanism, not a special case"; §20's own **Continuous vs. Triggered Composition** subsection is the exact split `ResolvedCue`/`TriggeredCue` below implement — it names a voice's audio cue as its standing-composition example and "a footstep's layered sound" as its triggered-composition one; §20's own **Audio Composition** subsection describes this library's real one-cue-per-voice shape directly, issue #160), [§4 Architectural Invariants](../../docs/specification/04-architectural-invariants.md) (determinism constraints this library's design follows throughout)

## What this round implements

- `atlas::audio::ResolvedCue` — a plain aggregate (rule of zero: no invariant beyond its four fields) reporting one voice's resolved, mix-ready state: `source` (`EntityRef`), `cue` (`ResourceId`), `effective_gain`, `effective_pan`.
- `atlas::audio::render(voices, cues, gains, pans)` — the mixer/composition function the issue asks for. It walks `voices` (a caller-supplied, explicitly ordered `std::span<const EntityRef>`) and, for each entity, looks up its composed cue/gain/pan from three real `atlas::runtime::PropertyStore<T>` instances (the same storage type `atlas::Context::get<T>()` reads through elsewhere in the runtime, per `atlas-runtime`'s own README). A voice missing *any* of the three properties this tick is skipped entirely — "not fully composed yet" is treated as "not currently audible," never defaulted or guessed at. Present voices have their gain clamped to `[0, 1]` and pan clamped to `[-1, 1]` (`clamp_gain`/`clamp_pan`, both `constexpr`) before being reported.
- The function never iterates a `PropertyStore` directly (each one is backed by `std::unordered_map`, whose iteration order isn't part of its contract) — it only ever looks entities up by the order the caller already fixed via `voices`, satisfying spec §4's "avoid unordered iteration... anywhere it could affect output" directly rather than by convention.
- `render()` reads no wall-clock time, no platform entropy, and no global/static state of any kind — it is a pure function of its four arguments. Given identical `PropertyStore` contents and an identical `voices` order, it returns bit-identical output on every call; `tests/atlas-audio/sound_renderer_test.cpp`'s `Render.RepeatedCallsWithIdenticalInputsProduceBitIdenticalOutput` asserts exactly that, matching this codebase's existing convention (per CLAUDE.md, `atlas-core`'s `Random`) of treating bit-exact repeatability as a real, checkable test category rather than an assumption.
- `Render.ConsumesGainComposedThroughTheRealPropertyCompositionEngine` (same test file) exercises the intended end-to-end pipeline explicitly: a gain value produced by `atlas::runtime::resolve_multiplicative` over real `atlas::runtime::Contribution<float>` values is stored into a `PropertyStore<float>` and only then handed to `render()` — proving this library integrates with `atlas-runtime`'s actual composition machinery rather than a hand-rolled stand-in for it.

## Scoping: no sample synthesis inside `render()` itself; real device I/O now lives in the backend

Issue #31 explicitly scoped its own pass to a "minimal TDD scaffold" and deferred real audio device I/O to a follow-up issue — at that point, no new third-party dependency (miniaudio, SDL, a platform audio API) had been added, and nothing in this library opened an audio device, decoded an audio file, or produced actual audible sound. **Issue #55 (see "Sdl3AudioBackend" below) has since built that follow-up for SDL3 specifically** — `Sdl3AudioBackend` now genuinely opens a device and plays real decoded PCM through it. What remains true from #31's original scoping, still deliberately: `render()` itself (`sound_renderer.hpp`) never touches a device, decodes a file, or synthesizes a sample — it stops at the resolved-entries list described above, exactly as before. Device I/O is entirely the backend's job (`AudioBackend::submit()`/`trigger()`), never `render()`'s.

A second, related scoping decision made back in #31 (the issue's own wording: *"your call, but make the reasoning explicit"*), still the load-bearing design choice today: **the "sound output" `render()` produces is the resolved-entries list described above, not a raw numeric sample buffer.** Two concrete reasons, not just "the lighter option was easier":

1. **`ResourceId` is a stable identity, nothing more — decoding is a separate, later step.** `render()` never touches decoded PCM at all; `atlas::audio::DecodeCache` (issue #164) is what turns a `ResourceId` into `DecodedClip` samples, and only `Sdl3AudioBackend` (or any other real backend) ever calls it. Baking synthesis into `render()` itself would mean this library manufacturing audio content out of nothing meaningful — which is exactly the "sound design" territory §24 keeps on the application side of the mechanism/meaning boundary, not a platform mechanism.
2. **The resolved-entries list is the direct analogue of what the sibling renderers in §19 already produce at this layer.** §19 describes the UI renderer's compositing layers as "producing draw calls rather than texture layers" — an intermediate, mixer-ready representation, not final pixels. `ResolvedCue` is that same shape for audio: a resolved, ready-to-mix description of what should be audible and how; `Sdl3AudioBackend` is the "actual DSP/PCM step" #31 anticipated a follow-up would build, consuming exactly this shape unchanged.

**SDL3 is the only real backend built so far.** A `MINIAUDIO` backend remains a documented, explicitly-not-ruled-out future option (issue #55's own architecture-decision writeup) if SDL3's own gaps — no native pan primitive, no automatic one-shot voice lifecycle (see below) — ever prove painful enough to justify a second audio dependency; it is not attempted in this round.

## Backend contract: `AudioBackend`, `NullAudioBackend`, sustained vs. triggered (issues #149, #159)

`include/atlas/audio/audio_backend.hpp` defines `atlas::audio::AudioBackend`, the compile-time concept (spec §5: "checked like a C++ concept, never a runtime interface table or virtual dispatch lookup") every backend — real or null — must satisfy, mirroring `atlas-render`'s `FrameBackend` (issue #148) exactly. `include/atlas/audio/null_audio_backend.hpp`'s `NullAudioBackend` is the always-buildable, zero-third-party-dependency backend selected by default; `libraries/atlas-audio/CMakeLists.txt`'s `ATLAS_AUDIO_BACKEND` CMake option (default `NULL`) picks which concrete backend a build compiles in at configure time — `SDL3` (issue #55, see "Sdl3AudioBackend" below) is the first real one; selecting anything else still fails with a clear message.

The concept has two independent requirements, matching spec §20's Continuous vs. Triggered Composition split rather than one undifferentiated cue list:

- **`submit(std::span<const ResolvedCue>)`** — this tick's full sustained/standing voice snapshot. `ResolvedCue::source` is the stable per-voice identity a conforming backend diffs each tick's list against the previous one by: an entity present last tick and absent this tick must be stopped. This is what makes interrupting a sustained sound — a channeled attack's wind-up hum cut short by a stun, or the caster's own movement breaking the cast — work for free: the capability that owns the channel just stops contributing that entity's cue property the tick it's interrupted, and every conforming backend reacts identically without atlas-audio itself ever expressing "stop" as its own concept. This is a documented contract obligation the concept cannot check structurally (same shape as `FrameBackend`'s culling comment, issue #117) — it does not change `ResolvedCue`'s fields.
- **`trigger(const TriggeredCue&)`** — one independent, fire-and-forget one-shot voice per call, with no standing value and no diffing; it always plays to completion regardless of any later `submit()` snapshot. `TriggeredCue` is the same four-field shape as `ResolvedCue` (`source`, `cue`, `gain`, `pan`, reusing `clamp_gain`/`clamp_pan`), for cases like `demo/modules/door`'s `DoorOpened` event carrying a cue `ResourceId` — a capability constructs a `TriggeredCue` itself and the host's tick loop calls `trigger()` directly; atlas-audio never learns what "door" means (spec §2, Mechanism Over Meaning).

`NullAudioBackend` implements both as no-ops — there's nothing for a backend that does nothing to track.

## `Sdl3AudioBackend`: real SDL3 device I/O (issue #55)

`include/atlas/audio/sdl3_audio_backend.hpp` + `src/sdl3_audio_backend.cpp` implement `atlas::audio::Sdl3AudioBackend`, the first real (non-null) `AudioBackend`, selected via `ATLAS_AUDIO_BACKEND=SDL3` (`libraries/atlas-audio/CMakeLists.txt` — the same `FetchContent`+`SYSTEM` SDL3 dependency `ATLAS_RENDER_BACKEND=SDL3`/`ATLAS_INPUT_BACKEND=SDL3` already take, at the same pinned `release-3.4.12` tag; `FetchContent_Declare`/`_MakeAvailable` are idempotent, so a build combining any of these SDL3 options fetches SDL3 once). It takes a `DecodeCache&` at construction (never owning it, same "must outlive" contract `DecodeCache` itself documents for its own `ResourceRegistry&`) and opens one shared SDL3 playback device.

**Architecture decision, superseding an earlier miniaudio-first draft of issue #55:** SDL3's own `SDL_AudioStream` model (one stream per voice, bound to a shared device, with `SDL_BindAudioStream`/`SDL_SetAudioStreamGain`/`SDL_PutAudioStreamData` all documented thread-safe from any thread — verified directly against the real fetched `SDL3/SDL_audio.h`, not assumed) gives the same real-time-safety property `ma_engine`/`ma_sound` would have, without a second third-party audio dependency. Two real, concrete gaps versus `ma_sound` remain and are both addressed explicitly below: SDL3 has **no pan primitive at all** (grepped the real header: zero matches for "pan"), and **no automatic one-shot voice lifecycle** (no `ma_engine_play_sound` equivalent).

### Device format decision

The device is opened at 48 kHz, 16-bit signed PCM (`SDL_AUDIO_S16`), with its channel count resolved from `Sdl3AudioBackendConfig::channels` (`ChannelMode::Stereo` by default and unchanged pre-#205 behavior — see "Startup-configurable channel mode" below) — even though every decoded source clip is mono (`wav_decoder.hpp`'s `canonical_channels == 1`). Stereo is deliberate: `ResolvedCue`/`TriggeredCue`'s entire reason for carrying a `pan` field is spreading one mono source across a stereo image, which is meaningless unless the device's own output actually has two independent channels to place that source between — a mono device would make pan silently unobservable. Every per-voice `SDL_AudioStream` is created with an identical `src_spec`/`dst_spec` (both equal to the device's own format), so SDL performs no channel up/downmixing of its own — by the time SDL sees a sample, this backend has already fully processed it.

### Pan law decision: equal-power (constant-power), not linear

Since SDL3 has no pan primitive, `Sdl3AudioBackend` hand-rolls panning as a stereo gain matrix baked directly into the samples it queues:

```
angle = (pan + 1) * (pi / 4)      // maps pan in [-1, 1] to [0, pi/2]
left_gain  = cos(angle)
right_gain = sin(angle)
```

At `pan == -1` (full left): `left_gain == 1`, `right_gain == 0`. At `pan == +1` (full right): the reverse. At `pan == 0` (center): `left_gain == right_gain ≈ 0.707` (each channel −3 dB) — `left_gain² + right_gain² == 1` at every pan value, so perceived *power* stays constant as a sound pans across the field, unlike a linear law (`left = (1-pan)/2`, `right = (1+pan)/2`), which would perceptibly dip in loudness at center. Equal-power is the standard choice for exactly this reason.

### Startup-configurable channel mode (issue #205)

Surfaced by PR review on #204: `device_channel_count` was originally a hardcoded `constexpr int = 2`. `Sdl3AudioBackendConfig` (mirroring `JoltPhysicsBackendConfig`'s own constructor-parameter precedent, issue #193, exactly) now exposes a `channels` field (`ChannelMode::Mono` or `ChannelMode::Stereo`, defaulting to `Stereo` so `Sdl3AudioBackend backend{decode_cache}` — every existing call site — keeps compiling and behaving identically), passed as a trailing, defaulted constructor parameter.

**"Configurable channel count" narrows to specifically mono vs. stereo, not an arbitrary N.** The equal-power pan law is fundamentally a 2-channel (left/right) gain matrix — it doesn't generalize to other channel counts without a different spatialization scheme entirely (real 5.1/7.1 surround needs per-speaker positioning, not a bigger version of the same gain matrix). `ChannelMode::Mono` is therefore not "channel count 1 of N" — it's the one specific alternative this backend supports: **no panning at all**. A voice's own `pan` field (`ResolvedCue::effective_pan`/`TriggeredCue::pan`) is still accepted in Mono mode but silently ignored — `to_output_samples()` (the `.cpp`) copies the clip's samples straight through unchanged rather than building a stereo gain matrix, the same "policy over crashing" precedent `sound_renderer.hpp`'s `clamp_gain`/`clamp_pan` set for an out-of-range value, applied here to "not applicable" rather than "out of range."

**A changing pan value on a Mono sustained voice never triggers the Stereo-only re-queue glitch.** Since pan has zero audible effect in Mono mode, `submit()`'s existing-voice path skips the `SDL_ClearAudioStream`/re-queue step entirely when `channels_ == ChannelMode::Mono` — paying that cost (and its restart-from-the-beginning glitch) for a value that can never change the output would be pure waste. `Sdl3AudioBackendTest.ChangingPanOnAMonoSustainedVoiceNeverReQueuesIt` proves this directly: rather than asserting an exact byte-count equality (which would itself be racy — ordinary device consumption between two reads changes the queued count with no bug present at all), it waits for the dummy driver to genuinely consume part of a long clip, then asserts the queued count never goes back *up* after a pan-only `submit()` — a re-queue would always reset it to the clip's full length, so "never increases" is a timing-independent way to detect one.

`Sdl3AudioBackendTest.MonoConfigQueuesHalfTheByteLengthStereoDoesForTheIdenticalClip` proves Mono mode is a genuinely different structural path (not a cosmetically-accepted config value): a Stereo voice's queued byte count for the identical clip is always exactly double a Mono voice's (interleaved L/R samples vs. the clip passed through unchanged). Both new tests use a much longer synthetic clip (`make_long_clip_registry`, `sdl3_audio_backend_test.cpp`) than the rest of this file's 5-sample fixture — the existing looping test's own tiny clip drains fast enough that reading queued-byte-counts back-to-back around it would themselves race against the dummy driver's real-time consumption.

### Gain vs. pan: an intentionally asymmetric update mechanism

`submit()`'s already-present-voice path treats gain and pan differently, on purpose:

- **Gain** has a native, thread-safe, non-destructive primitive (`SDL_SetAudioStreamGain`) that rescales already-queued/future audio without touching queued sample data or playback position — every `submit()` call re-applies it unconditionally, cheaply, whether or not it actually changed.
- **Pan** has no such primitive — it's baked into the sample bytes themselves. Changing it on an already-playing sustained voice requires `SDL_ClearAudioStream()` followed by a fresh `SDL_PutAudioStreamData()` call with the clip re-panned from the start. This is a real, documented limitation: **changing pan on a sustained voice restarts that voice's clip from the beginning** (a small audible glitch) rather than continuing seamlessly — an accepted trade-off given this round's "short one-shot sounds only, no streaming/long-form audio" scope, where a full clip is short enough that this is rarely noticeable. To avoid paying this cost on every tick a voice's *gain* alone changes, the re-queue only runs when pan's value actually differs from what was last baked in (tracked per-voice via `SustainedVoice::baked_pan`).

### Sustained-voice looping (ambiance)

A sustained voice must keep sounding for as long as its source keeps being submitted, even past its own clip's natural duration — the real motivating cases are **ambiance** (a looping wind/room-tone bed covering a whole zone) and a channeled effect's hum (`ResolvedCue`'s own doc comment, `sound_renderer.hpp`, names "a channeled attack's wind-up hum" as its motivating sustained-cue example), neither of which should fall silent partway through just because the underlying clip is shorter than the channel/zone itself. This was a real gap caught in review, not something the original design deliberately deferred: an earlier version of `submit()` queued a voice's panned samples exactly once at creation and never again, so any clip shorter than however long its source kept being submitted went silent for the remainder. Every `submit()` call now checks each already-tracked voice's own `SDL_GetAudioStreamQueued()` and, once it reaches `0` (the device has fully consumed what was queued), re-queues that same voice's already-baked stereo samples (`SustainedVoice::baked_stereo_samples`, kept around specifically so a loop never needs to re-decode or re-pan from `DecodeCache` on every iteration) from the start — a real, seamless-enough loop for this round's "full clip, no streaming" scope (true gapless/crossfaded looping, or looping a clip too long to fully decode into memory, is a separate, harder problem this backend does not attempt). `trigger()`'s own one-shot voices are deliberately excluded — they play once and are reaped on completion (see below), never looped. `Sdl3AudioBackendTest.SustainedVoiceLoopsPastItsOwnClipDurationWhileStillSubmitted` proves this against the real dummy driver's own real-time device-buffer pacing (`~21ms` at 48kHz/1024-sample-frame buffers, `src/audio/dummy/SDL_dummyaudio.c`) rather than asserting it in the abstract.

### Diff-by-source contract (issue #159)

`submit()` diffs this tick's `ResolvedCue` list against the previous tick's by `source`: an entity present last tick and absent this tick has its stream unbound and destroyed; a newly-present entity gets a freshly created and bound stream; an entity present in both ticks has its existing stream **updated in place** (per the gain/pan mechanism above), never recreated. Voices are tracked in a `std::vector<SustainedVoice>` (insertion-ordered, linearly searched by `source`) rather than a `std::unordered_map` — mirroring `demo/modules/rigid_body`'s `BodyRegistry` precedent for "deterministic, insertion-ordered per-entity registry" out of general code-quality habit, even though this presentation-only backend (§4/§20) doesn't need to satisfy the strict simulation-determinism bar capability code does.

### One-shot voice pool (`trigger()`)

SDL3 has no automatic lifetime management for a fire-and-forget sound. `trigger()` creates one independent `SDL_AudioStream` per call (never diffed against anything, never reused as a "same source" slot — two triggers from the same source are two unrelated voices) and detects when a triggered stream has fully drained its queued data via `SDL_GetAudioStreamQueued(stream) == 0` (reliable here because every stream's src/dst formats are identical, so nothing is ever buffered mid-conversion). Detection happens via a lazy sweep at the start of every `submit()`/`trigger()` call — never a background thread.

### Failure handling

A `ResolvedCue`/`TriggeredCue` referencing a `ResourceId` that fails to decode (`DecodeCacheStatus != Ok`) simply produces no voice for that tick/call — `submit()`/`trigger()` never throw or crash on a bad asset. Construction itself (opening the audio subsystem and default playback device) throws `std::runtime_error` with `SDL_GetError()`'s text included on failure, matching `Sdl3FrameBackend`/`Sdl3RawSignalSource`'s established convention exactly.

### Tests: a real device, not a mock

`tests/atlas-audio/sdl3_audio_backend_test.cpp` (built only when `ATLAS_AUDIO_BACKEND=SDL3`, mirroring `tests/atlas-render`'s/`tests/atlas-input`'s own SDL3-only test gating) runs against SDL3's real, always-available **"dummy" audio driver** (confirmed directly in the fetched SDL3 source, `src/audio/dummy/SDL_dummyaudio.c` — a genuine null-output backend, not a mock we wrote), forced via the `SDL_AUDIODRIVER=dummy` environment variable set on the whole test binary's process environment (`tests/atlas-audio/CMakeLists.txt`'s `gtest_discover_tests(... PROPERTIES ENVIRONMENT ...)`, the same mechanism `tests/atlas-render`'s own `LSAN_OPTIONS`/`VK_ICD_FILENAMES` environment uses). One real gotcha this surfaced (confirmed by reading `SDL_hints.c` directly, not assumed): a hint already set from a process environment variable silently wins over a later in-test `SDL_SetHint()` call at the default priority — the one test that needs to force an *invalid* driver (`Sdl3AudioBackendConstruction.FailureReportsSdlErrorTextInTheException`) has to use `SDL_SetHintWithPriority(..., SDL_HINT_OVERRIDE)` to actually override it.

## WAV decoder: canonical PCM format (issues #55, #163)

`include/atlas/audio/wav_decoder.hpp`'s `atlas::audio::decode_wav(std::span<const std::byte>)` is a hand-rolled WAV parser — no third-party dependency (no `dr_wav`, no miniaudio's own decoding path), matching this project's "hand-roll it when the format is trivial" precedent (FNV-1a, the resource blob format). It walks the RIFF chunk structure explicitly (skipping any chunk that isn't `"fmt "` or `"data"`, honoring the format's own odd-chunk-size padding byte) rather than assuming `"fmt "` is always immediately followed by `"data"` — real encoders commonly emit `"LIST"`/`"fact"` metadata chunks in between.

**Canonical PCM format, named explicitly rather than silently assumed (per #55's own scoping): 48 kHz, mono, 16-bit signed PCM.** Any WAV asset not already in this exact format is rejected (`WavDecodeStatus::UnsupportedFormat`), never resampled or reinterpreted — resampling stays explicitly out of scope. Mono, not stereo, is the load-bearing part of this decision: `ResolvedCue`/`TriggeredCue` already carry a `pan` field whose entire purpose is spreading a *single* source across stereo output — a pre-mixed stereo asset has no well-defined single answer for what pan should do to it, so this format matches what pan already assumes rather than introducing a second, incompatible notion of "stereo audio." 48 kHz is the de facto standard game-audio sample rate; 16-bit PCM is simple to hand-decode.

A malformed container (bad RIFF/WAVE magic, a missing `fmt `/`data` chunk, a chunk claiming more bytes than are actually present, a `fmt ` chunk too small to hold its required fields, a `data` chunk whose size isn't a whole multiple of the sample width) and a structurally-valid-but-wrong-format WAV are reported as two distinct statuses (`Malformed` vs. `UnsupportedFormat`) rather than one generic failure — matching `atlas::resource::Resolution`'s own status-plus-payload convention, never thrown: a malformed or wrong-format asset is an ordinary runtime condition (a bad export, a corrupted download), not a programmer error.

## Decode cache: ResourceId → decoded PCM (issues #55, #164)

`include/atlas/audio/decode_cache.hpp`'s `atlas::audio::DecodeCache` wraps a `atlas::resource::ResourceRegistry` reference plus `decode_wav()`, caching the result keyed by `ResourceId` so the same asset's bytes are never resolved or decoded more than once. `get_or_decode(id)` returns a `const DecodeCacheResult&` into the cache's own storage (no copy of the decoded samples on a cache hit).

**Every failure mode is reported, not collapsed into one generic status**, mirroring both layers it wraps: `Unresolved`/`ResolutionFailed` from `atlas::resource::ResolutionStatus`, `DecodeMalformed`/`DecodeUnsupportedFormat` from `WavDecodeStatus`. **Both successes and permanent failures are cached** — `ResourceRegistry`'s own blobs are loaded once at construction and never change underneath it, so retrying a resource that will never resolve differently is pointless.

**Encapsulated (not rule of zero)**, the same reasoning `ResourceRegistry`'s own header documents for its own class shape: it protects the real invariant that a cache entry stays consistent with the registry it was built from.

**Explicitly out of scope (per #164's own scoping, not silently assumed fine):**

- **Eviction policy.** This cache grows unboundedly for the process's lifetime — flagged as an open question, not solved here.
- **Thread-safety beyond the sim thread.** Every call in this round's design originates from the sim thread alone (`Sdl3AudioBackend::submit()`/`trigger()`, issue #55), never from the audio callback thread itself. A cache safe to call from the audio thread too is a different, harder problem this class does not attempt to solve.

## Dependency position

`atlas-audio` depends publicly on `atlas::runtime` (for `PropertyStore<T>`, and transitively `atlas::entity` for `EntityRef`) and `atlas::resource` (for `ResourceId`), plus `atlas_project_options`/`atlas_project_warnings` and the standard library — following the `atlas-core` CMake pattern exactly (`atlas_project_options` PUBLIC, `atlas_project_warnings` PRIVATE). Per §5 and §13, this is an **optional** library: a headless server host must never gain a dependency on `atlas-audio`, and nothing in `libraries/atlas-runtime`, `libraries/atlas-entity`, or any other non-optional library depends on it in the other direction. `atlas-audio` itself depends only downward (on runtime libraries and generated contracts), never on `atlas-render`, `atlas-ui`, `atlas-input`, or `atlas-editor` — each of those is a sibling optional library, not a dependency of this one.

## Open questions (flagging for human review, not silently resolved)

- **Gain/pan composition strategy.** This round treats gain and pan as ordinary composed `float` properties the caller resolves upstream (e.g. via `resolve_multiplicative` for gain, as the integration test demonstrates) before ever reaching `render()`. Spec §20 doesn't pin down which of the seven composition strategies is "correct" for pan specifically — Additive (a plausible fit, since multiple simultaneous stereo-position nudges would sum) is assumed by the integration test's shape but never enforced by this library, since `render()` accepts an already-resolved value and has no opinion on how it got there. Whoever writes the first real audio-emitting capability should confirm Additive is actually the right choice for pan before relying on it.
- **Gain ceiling of exactly 1.0.** `clamp_gain` hard-codes `[0, 1]` (unity gain as the ceiling). A capability wanting deliberately "louder than normal" emphasis (e.g. a boss-cue mix override) would need a different mechanism (a second, uncapped gain-multiplier stage downstream of this one) rather than this function's ceiling being configurable — left as a future decision rather than guessed at now, since nothing in this round's scope needs it.
- **One *sustained* cue per voice, still — resolved as intentional (issue #160).** `render()`'s three `PropertyStore`s model exactly one active sustained cue per entity — issues #149/#159 resolve the *triggered* (one-shot) half of this via `TriggeredCue`/`trigger()`, which needs no per-entity voice slot at all, but a capability wanting an entity to sustain several simultaneous *standing* cues (e.g. a looping footstep sound *and* a looping aura hum on the same entity at once) still needs multiple voice `EntityRef`s (one per concurrent sustained cue). Spec §20's Audio Composition subsection previously described a single `ActiveAudioSources` property accumulating multiple sources into one mixed graph (`ParticleEffects`-shaped) — issue #160 reconciled that mismatch by updating §20's wording to describe this one-cue-per-voice model as the deliberate design, rather than changing the implementation to match the old wording. A richer per-entity multi-sustained-voice or true accumulating-collection shape remains an option for a future revision if a capability author needs it, not something ruled out by this decision.
- **Real device I/O — resolved for SDL3 (issue #55), still open for any other backend.** `Sdl3AudioBackend` (see its own section above) now genuinely opens a device and plays real decoded PCM; `render()` itself still never touches a device or synthesizes a sample (see "Scoping" above), and that boundary is unchanged. A `MINIAUDIO` backend remains a documented, not-ruled-out future option per #55's own writeup if SDL3's hand-rolled pan law or one-shot pool bookkeeping ever prove painful — not attempted this round.
- **Pan-change glitch on a sustained voice (issue #55).** `Sdl3AudioBackend` restarts a sustained voice's clip from the beginning whenever its pan changes (no native SDL3 pan primitive to update in place — see its own "Gain vs. pan" section above for the full reasoning). Acceptable given this round's short-one-shot-clip scope, but a capability that pans a long-held sustained voice continuously (e.g. tracking a fast-orbiting entity) would hear it restart on every change — flagged here rather than silently accepted as a hidden constraint.
- **One-shot voice pool has no hard cap (issue #55).** `Sdl3AudioBackend::trigger()` creates a new `SDL_AudioStream` on every call with no configurable maximum concurrent one-shot count and no priority/stealing policy if very many trigger in the same tick — reaped lazily once drained, but nothing currently bounds how many can be in flight at once. Left unaddressed since nothing in this round's scope exercises that volume.
- **Only Mono and Stereo — no true surround (issue #205).** `Sdl3AudioBackendConfig::channels` only supports two concrete values; real 3+ channel/surround output would need a genuinely different spatialization scheme (per-speaker positioning), not a bigger version of the equal-power gain matrix this backend implements — a separate, larger effort if a game ever needs it, not attempted here.
