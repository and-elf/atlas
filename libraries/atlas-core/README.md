# atlas-core

**Status:** Seeded. Implements `atlas::core::SemanticVersion` (see `include/atlas/core/semantic_version.hpp`), a comparable major/minor/patch value type used for contract version resolution and enforcement (§6, §13); `atlas::core::Time` (`include/atlas/core/time.hpp`), a tick-count simulation-time value type; and `atlas::core::Random` (`include/atlas/core/random.hpp`), a deterministic seeded pseudo-random stream — the built-in deterministic `Time`/`Random` types §4 (Architectural Invariants — Determinism) requires simulation logic to source time and randomness from instead of platform wall-clock/entropy. Nothing else in this library's eventual scope is implemented yet.

## Scoping decisions: `Time` and `Random`

Spec §4 states the requirement this library-level task fills: "Capabilities that require randomness or time must source it from runtime-provided, built-in deterministic types rather than platform or language facilities," and that Random is "seeded explicitly, produces an identical sequence of values for a given seed on every platform." Before writing `Time`/`Random`, no such type existed anywhere in the tree (`grep -rn "class Time\|struct Time\|class Random\|struct Random" libraries/` came back empty) — this is genuinely the first implementation, not a refinement of an existing one.

**`Time` is a tick count, not a wrapper around `std::chrono`'s clocks.** `Time::ticks` is a plain `std::uint64_t`; nothing in its own logic ever calls `std::chrono::system_clock`/`steady_clock` — doing so would reintroduce exactly the non-reproducible input §4 rules out. `Time` does use `std::chrono::duration<double>` as the *return type* of `to_duration()`, but only as a value-holding vocabulary type for a presentation-facing conversion (audio/render interpolation, per §4's carve-out) — no clock is ever read to produce it, and its own doc comment says explicitly that the result must never feed back into simulation state. `ticks_per_second = 60` is this library's default fixed-timestep rate: a widely-used baseline for real-time simulations (many game/server simulations tick at a rate in this vicinity), not a value spec §4 mandates — flagged below as an open question rather than asserted as settled. Rule of Zero applies directly: the only invariant is a *usage* discipline ("don't treat this as wall-clock time"), which a constructor cannot enforce, so `Time` stays a plain aggregate with defaulted comparison.

**`Random` uses `std::mt19937_64` as its engine, verified against the standard's own wording rather than assumed.** The C++ standard specifies `std::mersenne_twister_engine` (what `mt19937_64` is a named specialization of) by exact transition and generation formulas over its template parameters (word size, state size, tempering shifts/masks, and so on) — this is a fully-specified algorithm, not one merely constrained by statistical output properties. Two conforming standard library implementations seeded identically are therefore required to produce a bit-identical sequence of raw engine outputs — exactly the "identical sequence... on every platform" guarantee §4 asks for, and checkable directly from how the standard defines the engine rather than taken on faith.

That verification stops at the engine, though, and this is the non-obvious finding worth flagging: **`std::uniform_int_distribution` (the obvious choice for `next_in_range()`) is not covered by the same guarantee.** The standard specifies distributions only by the mathematical distribution they must approximate, not by a required bit-exact algorithm for mapping engine output to a bounded value — libstdc++ (Linux/GCC, this repo's default), libc++ (macOS/Clang), and MSVC STL (Windows) are all free to implement that mapping differently, and in practice do not agree. Since CLAUDE.md's cross-platform deployment targets are exactly those three standard libraries, reaching for `std::uniform_int_distribution` here would have silently reintroduced the cross-machine non-determinism this type exists to eliminate — a subtle enough trap that it's worth naming explicitly rather than leaving for a future bug report. `next_in_range()` instead implements its own bounding directly on `next_u64()` (`src/random.cpp`): the classic `arc4random_uniform`-style approach of rejecting draws below `2^64 mod bound` (computed via unsigned wraparound to avoid representing `2^64` directly) before reducing modulo `bound`, which removes modulo bias using only the engine's own portably-specified output.

`Random` is an encapsulated class, not a rule-of-zero aggregate — deliberately, per CLAUDE.md's guidance to reach for encapsulation only when there's a real invariant to protect: here it's "the underlying engine only ever advances through this type's own draw methods," never re-seeded or read mid-stream by a caller, since two capabilities silently perturbing a stream they're meant to share in a fixed order (§4's per-host stream diagram) would itself be a determinism defect. `next_u32()`/`next_u64()`/`next_in_range()` each advance the engine by exactly one step per call regardless of requested width, so a capability author reasoning about "how many draws has this stream consumed so far" never has to special-case which method was called — `next_in_range()`'s rejection loop is the one documented exception, consuming more than one step on the rare draws it must reject, which is inherent to correct rejection sampling rather than a deviation from that rule.

Per the assignment's explicit scope, this round deliberately does **not** include: a wall-clock `now()` convenience (even presentation-only — a separate future concern), floating-point random distributions, or a global/thread-local default `Random` instance (the per-host seeded stream is a host-owned resource, a future `atlas-runtime` concern to own and seed, not something this library should make ambient).

**Open questions (flagging for human review, not silently resolved):**

- `ticks_per_second = 60` is a library-wide `constexpr` constant. Spec §4 requires *a* fixed, deterministic tick rate but does not mandate 60 specifically, and different hosts (e.g. a competitive-latency-sensitive capability vs. a background simulation) might reasonably want different rates. Whether this should stay a single library-wide constant or become a per-host/per-composition configuration parameter (and if so, how `Time` values from hosts running different rates would ever legitimately compare) is left for whoever designs `atlas-runtime`'s host composition to decide.
- `Random::next_in_range()` takes an inclusive `[min, max]` of `std::uint64_t`. There is no signed-range or floating-point overload — deliberately, per the assignment's "keep the surface small" instruction — but real capability code will likely want a signed-integer range at some point (e.g. a damage roll expressed as `int`). Whether that becomes a second overload on this type or a capability-side conversion around `next_in_range()` is left open rather than guessed at now.
- `next_u32()` truncates one `next_u64()` draw to its low 32 bits rather than buffering the unused high 32 bits for a subsequent call. This is the simpler design (one call always equals one engine step, discussed above) but "wastes" half of every draw when a caller only ever needs 32-bit values. Flagging in case a reviewer considers that waste significant enough to justify the added state a buffering scheme would need.

## Dependency position

`atlas-core` is the foundation of the dependency graph (§5): it depends on nothing else in `libraries/`, only on the standard library and the shared `atlas_project_options`/`atlas_project_warnings` interface targets. Every other library is expected to sit at or above it.
