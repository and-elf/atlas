# atlas-core

**Status:** Seeded. Implements `atlas::core::SemanticVersion` (see `include/atlas/core/semantic_version.hpp`), a comparable major/minor/patch value type used for contract version resolution and enforcement (§6, §13); `atlas::core::Time` (`include/atlas/core/time.hpp`), a tick-count simulation-time value type; and `atlas::core::Random` (`include/atlas/core/random.hpp`), a deterministic seeded pseudo-random stream — the built-in deterministic `Time`/`Random` types §4 (Architectural Invariants — Determinism) requires simulation logic to source time and randomness from instead of platform wall-clock/entropy. `Random` provides unsigned (`next_u32`/`next_u64`/`next_in_range`), signed-range (`next_in_range_i64`), and floating-point (`next_double`/`next_double_in_range`) draws. Nothing else in this library's eventual scope is implemented yet.

## Scoping decisions: `Time` and `Random`

Spec §4 states the requirement this library-level task fills: "Capabilities that require randomness or time must source it from runtime-provided, built-in deterministic types rather than platform or language facilities," and that Random is "seeded explicitly, produces an identical sequence of values for a given seed on every platform." Before writing `Time`/`Random`, no such type existed anywhere in the tree (`grep -rn "class Time\|struct Time\|class Random\|struct Random" libraries/` came back empty) — this is genuinely the first implementation, not a refinement of an existing one.

**`Time` is a tick count, not a wrapper around `std::chrono`'s clocks.** `Time::ticks` is a plain `std::uint64_t`; nothing in its own logic ever calls `std::chrono::system_clock`/`steady_clock` — doing so would reintroduce exactly the non-reproducible input §4 rules out. `Time` does use `std::chrono::duration<double>` as the *return type* of `to_duration()`, but only as a value-holding vocabulary type for a presentation-facing conversion (audio/render interpolation, per §4's carve-out) — no clock is ever read to produce it, and its own doc comment says explicitly that the result must never feed back into simulation state. `ticks_per_second = 60` is this library's default fixed-timestep rate: a widely-used baseline for real-time simulations (many game/server simulations tick at a rate in this vicinity), not a value spec §4 mandates — flagged below as an open question rather than asserted as settled. Rule of Zero applies directly: the only invariant is a *usage* discipline ("don't treat this as wall-clock time"), which a constructor cannot enforce, so `Time` stays a plain aggregate with defaulted comparison.

**`Random` uses `std::mt19937_64` as its engine, verified against the standard's own wording rather than assumed.** The C++ standard specifies `std::mersenne_twister_engine` (what `mt19937_64` is a named specialization of) by exact transition and generation formulas over its template parameters (word size, state size, tempering shifts/masks, and so on) — this is a fully-specified algorithm, not one merely constrained by statistical output properties. Two conforming standard library implementations seeded identically are therefore required to produce a bit-identical sequence of raw engine outputs — exactly the "identical sequence... on every platform" guarantee §4 asks for, and checkable directly from how the standard defines the engine rather than taken on faith.

That verification stops at the engine, though, and this is the non-obvious finding worth flagging: **`std::uniform_int_distribution` (the obvious choice for `next_in_range()`) is not covered by the same guarantee.** The standard specifies distributions only by the mathematical distribution they must approximate, not by a required bit-exact algorithm for mapping engine output to a bounded value — libstdc++ (Linux/GCC, this repo's default), libc++ (macOS/Clang), and MSVC STL (Windows) are all free to implement that mapping differently, and in practice do not agree. Since CLAUDE.md's cross-platform deployment targets are exactly those three standard libraries, reaching for `std::uniform_int_distribution` here would have silently reintroduced the cross-machine non-determinism this type exists to eliminate — a subtle enough trap that it's worth naming explicitly rather than leaving for a future bug report. `next_in_range()` instead implements its own bounding directly on `next_u64()` (`src/random.cpp`): the classic `arc4random_uniform`-style approach of rejecting draws below `2^64 mod bound` (computed via unsigned wraparound to avoid representing `2^64` directly) before reducing modulo `bound`, which removes modulo bias using only the engine's own portably-specified output.

`Random` is an encapsulated class, not a rule-of-zero aggregate — deliberately, per CLAUDE.md's guidance to reach for encapsulation only when there's a real invariant to protect: here it's "the underlying engine only ever advances through this type's own draw methods," never re-seeded or read mid-stream by a caller, since two capabilities silently perturbing a stream they're meant to share in a fixed order (§4's per-host stream diagram) would itself be a determinism defect. `next_u32()`/`next_u64()`/`next_in_range()` each advance the engine by exactly one step per call regardless of requested width, so a capability author reasoning about "how many draws has this stream consumed so far" never has to special-case which method was called — `next_in_range()`'s rejection loop is the one documented exception, consuming more than one step on the rare draws it must reject, which is inherent to correct rejection sampling rather than a deviation from that rule.

Per the assignment's explicit scope, this round deliberately does **not** include: a wall-clock `now()` convenience (even presentation-only — a separate future concern), or a global/thread-local default `Random` instance (the per-host seeded stream is a host-owned resource, a future `atlas-runtime` concern to own and seed, not something this library should make ambient).

## Signed-range and floating-point draws (`next_in_range_i64`, `next_double`, `next_double_in_range`)

Issue #87 resolved the "signed-range/floating-point" open question the initial round left open (previous paragraph in this README): real capability code does want a signed-integer range (e.g. a damage roll expressed as `int`) and a floating-point draw, so both were added directly to `Random` rather than as a capability-side conversion helper — the per-stream invariant above ("the engine only ever advances through this type's own draw methods") applies just as much to a signed or floating-point draw as to an unsigned one, so it belongs on the type that owns the engine, not bolted on from outside.

**`next_in_range_i64(std::int64_t min, std::int64_t max)`** is the signed counterpart of `next_in_range()`, returning a value uniformly distributed over `[min, max]` inclusive (throwing `std::invalid_argument` if `min > max`). It is a *distinctly named* method, not a same-named overload of `next_in_range()`: an ordinary call like `next_in_range(10, 20)` with plain `int` literals would become ambiguous between `(std::uint64_t, std::uint64_t)` and `(std::int64_t, std::int64_t)` candidates, since both are equally-ranked integral conversions from `int` — overloading purely on signedness here would silently break every existing unsigned call site. The implementation reinterprets each signed bound as its same-width unsigned bit pattern (`static_cast<std::uint64_t>`), computes the span via unsigned wraparound arithmetic — well-defined two's-complement modular arithmetic since C++20, the same "avoid representing 2^64 directly" trick `next_in_range()` already uses one layer up — and delegates to `next_in_range(0, span)` for the actual draw. That delegation is deliberate: it reuses `next_in_range()`'s unbiased rejection-sampling logic unchanged rather than re-deriving bias elimination for a second numeric type.

**`next_double()`** returns a `double` uniformly distributed over `[0, 1)`. It is built on the classic 53-bit-mantissa technique — keep the high 53 bits of one `next_u64()` draw (a `double`'s full mantissa precision) and scale by `2^-53` — rather than `std::uniform_real_distribution`, for exactly the reason `next_in_range()`'s doc comment (and the paragraph above) gives for avoiding `std::uniform_int_distribution`: the standard specifies the distribution only by its output distribution, not by a required bit-exact mapping from engine output to a bounded value, so different standard libraries are free to (and do) disagree. `2^-53` is exactly representable in IEEE-754 `binary64`, so the single multiplication is the only rounding step in the whole computation, and it follows the same round-to-nearest default on every platform this project targets — `-ffp-contract=off` (set unconditionally per CLAUDE.md) is what stops a fused multiply-add from folding that multiplication into a different rounding step on FMA-capable hardware, which is exactly the kind of platform-dependent rounding this method has to avoid.

**`next_double_in_range(double min, double max)`** is the floating-point counterpart of `next_in_range()`: `min + next_double() * (max - min)`, uniformly distributed over `[min, max)` — half-open, matching both `std::uniform_real_distribution`'s own convention and the natural range of the `next_double() * span` transform it's built on. It throws `std::invalid_argument` if `min > max` or either bound is NaN (checked as `!(min <= max)`, which is false — and therefore throws — for a NaN operand exactly because IEEE-754 comparisons involving NaN are themselves always false). No degenerate-range (`min == max`) special case is needed: the span is then exactly `0.0`, and `next_double() * 0.0` is exactly `0.0` for any finite `next_double()` result, so the formula already returns `min` exactly.

All three follow the one-call-equals-one-engine-step-of-`next_u64()` convention `next_in_range()` established, with the same single documented exception: `next_in_range_i64()` inherits `next_in_range()`'s rejection loop (consuming more than one step on the rare rejected draws), and is not a second, independent source of that exception.

**Decided (#86): tick rate becomes a per-host startup-configuration parameter, defaulting to 60Hz — not a single library-wide constant.** Confirmed directly by the repo owner: "Should be 60Hz unless configured through startup configuration. Also, server and client should not need the same frequency." This is the same idiom already established twice elsewhere in this codebase for "per-host behavior that isn't itself simulation logic": `Host`'s `has_authority` bool, required at construction and never changed afterward (`atlas-runtime`'s README), and `atlas-physics`'s `JobSystem` threading mode/`max_bodies` (issue #193) — decided once, at startup, per host, not a global constant and not mutable mid-session. `ticks_per_second` follows the identical shape: `Time` keeps `60` as its *default*, but the rate a given host actually runs at becomes a constructor-time parameter (mirroring `Host(StageSequence, bool has_authority)`'s own pattern), fixed for that host's entire lifetime — which is exactly what preserves bit-exact replay within one host's session regardless of what rate a *different* host happens to run at.

This also answers the sub-question the original issue posed but didn't resolve: **how would `Time` values from differently-configured hosts ever legitimately compare?** They don't need to, and nothing requires them to. A raw tick count is a host-local unit — only meaningful relative to that host's own configured rate. Nothing in property replication compares raw tick counts across hosts at all; it carries already-resolved property values (`Position`, `Health`, ...), which are rate-independent by construction. The one place tick counts *do* need a rate-independent interpretation — presentation-layer interpolation — already goes through `to_duration()`, converting ticks to seconds; once the rate is configurable, `to_duration()` simply needs to use *that host's own* configured rate rather than a hardcoded `60`, and the "reason about elapsed time in seconds, never raw ticks, across any boundary that might not share a rate" property holds automatically.

**Real migration cost this doesn't attempt to hide:** at least one existing call site (`demo/modules/movement/movement.cpp`'s `on_move`) currently reads `core::Time::ticks_per_second` as a bare global constant. Once the rate is per-host, that and any other such call site need to read it from the host/context instead (mirroring how `ctx.host().has_authority()` already works) — real, separate follow-up implementation work, not attempted by this decision alone.

**Open questions (flagging for human review, not silently resolved):**

- `next_u32()` truncates one `next_u64()` draw to its low 32 bits rather than buffering the unused high 32 bits for a subsequent call. This is the simpler design (one call always equals one engine step, discussed above) but "wastes" half of every draw when a caller only ever needs 32-bit values. Flagging in case a reviewer considers that waste significant enough to justify the added state a buffering scheme would need.
- `next_double()`/`next_double_in_range()` only offer `double` precision, not `float`. Nothing in the current capability scope has asked for single-precision draws, and `double` is the narrower-surface choice (one floating-point width to reason about, matching `Time::to_duration()`'s existing use of `double`); revisit if a caller ever has a concrete need for `float` specifically.

## Dependency position

`atlas-core` is the foundation of the dependency graph (§5): it depends on nothing else in `libraries/`, only on the standard library and the shared `atlas_project_options`/`atlas_project_warnings` interface targets. Every other library is expected to sit at or above it.
