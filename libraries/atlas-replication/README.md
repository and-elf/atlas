# atlas-replication

**Status:** Seeded, plus a generic property codec (issue #18). Implements `atlas::replication::write_entity_ref` and `atlas::replication::read_entity_ref` (`include/atlas/replication/entity_ref_codec.hpp`) — a matched encode/decode pair that puts `atlas::EntityRef` on the wire as an explicit little-endian `index` field followed by an explicit little-endian `generation` field, built on `atlas::serialization::ByteWriter`/`ByteReader` rather than a memcpy of `EntityRef`'s native layout. `read_entity_ref` fails explicitly (`std::nullopt`) if either field is truncated, the same past-the-end behavior `ByteReader` already gives every fixed-width read. Also implements the same pattern for `atlas::ResourceId`: `atlas::replication::write_resource_id`/`read_resource_id` (`include/atlas/replication/resource_id_codec.hpp`) put its single `value` field on the wire as one explicit little-endian `u64`, with `read_resource_id` failing explicitly (`std::nullopt`) on a truncated buffer the same way. Nothing else in this library's eventual scope (resource/state replication, delta compression, network transport) is implemented yet.

**PropertyId, and a generic reflection-driven property field codec (issue #18):** `atlas::PropertyId` (`include/atlas/replication/property_id.hpp`) is the same shape as `atlas::ResourceId` — a `std::uint64_t` derived from an authored name via `from_name` (FNV-1a, null sentinel for an empty name, `constexpr` since issue #23 for the same compile-time-usability reason as `ResourceId::from_name` — see `atlas-resource`'s own README) — but names a *property* generically for the replication/wire boundary rather than a resource. `write_property_id`/`read_property_id` (`property_id_codec.hpp`) mirror `resource_id_codec.hpp` exactly (a single little-endian `u64`). `write_property_fields`/`read_property_fields` (`property_codec.hpp`) go further: built on `atlas::reflection::for_each_field`/`field_types_t`, they put *any* `FieldVisitable` aggregate's direct fields on the wire in declaration order, generically — no hand-written `write_health`/`read_health`-style function per property type. Field types supported: every fixed-width primitive `ByteWriter`/`ByteReader` already implement (`int8`..`int64`, `uint8`..`uint64`, `float`, `double`), **and, as of issue #21, a field that is itself a `FieldVisitable` aggregate** (`EntityRef`, `ResourceId`, `PropertyId`, or any other plain struct of supported fields) — recursed into exactly the same way a top-level property's own fields are visited, genuinely (a struct field containing another struct field works, not just one hard-coded extra level). A field of any other shape (a pointer, a container, a non-aggregate class) is a compile error — no overload of `detail::write_one_field`/`read_one_field` is viable for it — not a silently wrong encoding or a runtime failure. `demo/tests/simulated_host.hpp`'s `replicate_health_to` is the worked example: it encodes `health::Health` as `(PropertyId::from_name("Health"), current, maximum)` through this generic path instead of calling `health::write_health`/`read_health` directly (those hand-written functions still exist, still exercised by `health_test.cpp`'s own round-trip test — deleting them is a follow-up once a second property also migrates, not decided by one worked example alone).

**Scoping decisions:**
- This is deliberately the smallest real slice of "state synchronization" that stands on its own: naming an entity (or a resource) on the wire is the prerequisite for replicating anything *about* it (spec §6, Server Authority: "Replication distributes observable state from authoritative hosts" — there is no observable state about an entity or resource without first being able to identify it). Everything downstream of this is out of scope for this round.
- Property replication *strategies* ("replicate contributions" vs. "replicate effective value", spec §20 Networking and Replication) are still explicitly deferred — `write_property_fields`/`read_property_fields` move a property's current field values onto the wire generically; they don't decide what "current value" means for a property multiple capabilities compose into (§20's Additive/Multiplicative/... strategies are a runtime-simulation concern, unaffected by this library). This applies equally to `ResourceId`: spec §20 notes resources compose the same way properties do, so a resource replication strategy is deferred for the same reason.
- The generic field codec covers both primitive fields and struct-typed (`FieldVisitable`) fields, recursively (issue #21) — `health::Health` (two `int32` fields) and a hypothetical property with an `EntityRef`- or `ResourceId`-typed field are both fully covered by the same mechanism. What remains out of scope is any field shape `atlas-cgen`'s manifest schema can't even express today (a list/array field, a field typed as another *composed* property) — not attempted speculatively ahead of a manifest type that would need it.
- Actual network transport/delivery (sockets, connections, reliability) is explicitly out of scope per spec §13 — `atlas-replication`'s responsibility is the replication *mechanism* (what goes on the wire and how it's framed), not networking I/O.
- Wire format is `index` then `generation`, each a plain `u32`, for `EntityRef`; a single plain `u64` for `ResourceId`/`PropertyId`; each field's own fixed width, in declaration order, for a generic property — no varint/delta encoding, no bit-packing anywhere. Every field involved is already fixed-width, so anything more elaborate would be premature optimization ahead of a real usage site; a future capability-composed replication frame can wrap any of these codecs however it needs to.
- All of these codecs' functions take `ByteWriter`/`ByteReader` directly (no type-specific stream type) — consistent with how atlas-serialization's own fixed-width `write_*`/`read_*` calls compose into whatever larger buffer a caller is building, letting any of them sit inline in a larger message alongside other fields without their own framing.
- `PropertyId` is physically owned by this library rather than a dedicated "atlas-property" library — unlike `EntityRef`/`ResourceId`, a property has no other domain-identity library today, and replication is `PropertyId`'s sole reason to exist so far.

**Provides:** state synchronization, replication mechanisms, network data distribution.

**Spec:** [§13 Library Architecture](../../docs/specification/13-library-architecture.md#library-responsibilities) (responsibility), [§6 Server Authority](../../docs/specification/06-server-authority.md) (Request Validation and Reconciliation — "confirm / replicate new state", the reason entity identity needs to cross the wire at all), [§20 Property and Resource Composition](../../docs/specification/20-property-and-resource-composition.md#networking-and-replication) (property replication strategies, deliberately deferred), [§4 Architectural Invariants](../../docs/specification/04-architectural-invariants.md) (deterministic execution — the reason encoding is explicit-endianness rather than native-layout)

## Dependency position

`atlas-replication` depends on `atlas::entity` (for `EntityRef`), `atlas::resource` (for `ResourceId`), `atlas::serialization` (for `ByteWriter`/`ByteReader`), and `atlas::reflection` (for `for_each_field`/`field_types_t`, backing the generic property codec), all linked `PUBLIC` since the codecs' public headers expose each dependency directly, plus `atlas_project_options`/`atlas_project_warnings` and the standard library. Per §5, it may depend on further lower-level libraries and generated contracts as replication's scope grows, never upward on capabilities, applications, or editor/deployment-specific code.
