# atlas-runtime

**Status:** Seeded. Implements `atlas::runtime::Host` (`include/atlas/runtime/host.hpp`) — the concrete runtime object a server or client process actually instantiates to hold state and drive execution. A `Host` owns an `atlas::entity::EntityRegistry` and an `atlas::scheduler::Scheduler` (constructed from an `atlas::stage::StageSequence`), and exposes:

- authority: `has_authority() const` — a plain bool, set once at construction (see Scoping decisions — the open question a previous round of this README left undecided).
- entity lifecycle: `create_entity()`, `destroy_entity(EntityRef)`, `is_entity_alive(EntityRef) const` — each delegating directly to the owned `EntityRegistry`.
- tick execution: `schedule(const StageId&, Job)`, `run_tick() const`, `sequence() const` — each delegating directly to the owned `Scheduler`.

Also implements `atlas::runtime::PropertyStore<T>` (`include/atlas/runtime/property_store.hpp`) — generic per-entity storage for one property type, the storage side of `atlas::Context::get<T>()` — and, in `include/atlas/runtime/property_composition.hpp`: `atlas::runtime::Contribution<T>` (carrying a `Lifetime` tag alongside its source and value) and `atlas::runtime::resolve_additive<T>` / `resolve_multiplicative<T>` (spec §20's Additive and Multiplicative composition strategies — the two of seven with a working evaluator so far).

Also implements `atlas::Context` (`include/atlas/runtime/context.hpp`) — the typed context a capability's request handler receives, matching spec §21's worked example call-by-call: `ctx.get<T>(entity)` (a monadic `std::optional<std::reference_wrapper<T>>`, reading through a registered `PropertyStore<T>`), `ctx.publish<T>(event)` (synchronous, in-registration-order dispatch to anything that `ctx.subscribe<T>(handler)`'d), and `ctx.host()` (exposing `has_authority()`). Lives in the top-level `atlas` namespace, not `atlas::runtime` — the same convention `EntityRef`/`RequestResult` already follow — even though the header is physically owned by this library. `Context` is deliberately domain-agnostic: `get`/`publish`/`subscribe` are templates operating on whatever `T` a capability's own contract declares, using type-erased (`std::any` keyed by `std::type_index`) maps internally rather than any hard-coded list of known property/event types.

**Scoping decisions:**

- This is deliberately **not** the eventual capability-composed host described in §7 (Host Composition) and §8 (Atlas Hosts) — that version is assembled by Atlas tooling from capability manifests (`depends_on`, `contracts.consumes`/`produces`, §13/§14), and neither the manifest format's code-generation step nor a host manifest reader exists in this repository yet. Building or hand-simulating that layer was explicitly out of scope for this slice. `Host` is instead the hand-composed runtime substrate such a manifest-driven host would eventually sit on top of: the concrete object a process new()'s up today, composed only from systems that already exist for real in this repo (`atlas-entity`, `atlas-stage`, `atlas-scheduler`).
- `Host` is an encapsulated class (private members + delegating methods), not a plain aggregate, even though it adds no invariant of its own beyond what `EntityRegistry` and `Scheduler` already protect internally: its entire reason to exist is to be the single owner composing those two systems, so there is no public field a caller could usefully set directly without going through one of the delegating methods.
- `schedule()`/`run_tick()`/`sequence()` are thin pass-throughs to the owned `Scheduler`, and `create_entity()`/`destroy_entity()`/`is_entity_alive()` are thin pass-throughs to the owned `EntityRegistry` — `Host` adds no additional validation or business logic beyond delegation. This matches the assignment's framing of `atlas-runtime` at this stage: proving out "coordination between systems" using only what already concretely exists, not inventing new behavior ahead of the systems that would need it (request routing, replication, resource resolution — none of which exist yet either).
- **Authority is now decided**: a plain `bool`, required at construction (`Host(stage::StageSequence, bool has_authority)`), never changed afterward. This resolves the open question a previous round of this README left explicitly undecided, once a real call site (a `Context`-based request handler checking `ctx.host().has_authority()`, matching §21's worked example verbatim) existed to design against rather than guess ahead of. A richer representation — distinct `ServerHost`/`ClientHost` types, or a capability-level concern layered on top — remains possible later; this is deliberately the smallest thing that answers the one question §21's handler code actually asks. See Open questions below for what's *not* resolved by this.
- `PropertyStore<T>`/`Contribution<T>`/`resolve_additive<T>`/`resolve_multiplicative<T>` are deliberately domain-agnostic (spec §2, Mechanism Over Meaning): none of them know what `T` represents, only that it's storable. Additive and Multiplicative are the two of §20's seven composition strategies implemented so far — see `property_composition.hpp`'s header comment for why the other five (each with genuinely different resolution semantics — a winner among candidates, an ordered merge, a proportional blend) don't generalize from either and are each their own future increment.
- `Contribution<T>` gained a `Lifetime` field (`Permanent`/`Duration`/`UntilEvent`/`WhileCondition`), defaulted to `Permanent` so every existing `{.source = ..., .value = ...}` call site is unaffected — but it's purely descriptive metadata this round, not something any function here branches on. An earlier version of this change also added `remove_contributions_by_source<T>`, reasoning that a `WhileCondition` contribution (e.g. a range-based aura) would need an explicit removal call the instant its governing condition failed, mirroring how `add_contribution`-style functions already push a new entry. That reasoning didn't survive contact with what `WhileCondition` actually means: nothing *fires* an event when a condition like "is the target still in range" stops holding — it's a fact about the current tick, not an occurrence, so there is nothing to react to and no discrete moment to call a removal function at. The correct model is that a `WhileCondition` contribution is never stored at all: it's constructed fresh every tick by whichever capability owns the condition and fed directly into `resolve_additive`/`resolve_multiplicative` alongside whatever `Permanent` contributions are already stored — both already accept a plain `std::span`, so no new primitive was needed once the model was corrected. `remove_contributions_by_source<T>` was reverted before anything used it, rather than merged and left dead. `Duration`/`UntilEvent` remain unimplemented: each needs its own associated data (a tick countdown; an event type to listen for) a bare enum tag can't carry, and nothing consumes them yet.
- `PropertyStore<T>` required adding a `std::hash<atlas::EntityRef>` specialization to `atlas-entity` (previously only `atlas::ResourceId` had one) so `EntityRef` could key a `std::unordered_map` — combines both fields (index, generation) rather than reusing one directly, since neither field alone is well-distributed the way `ResourceId`'s single already-random hash value is.
- `Context` borrows `PropertyStore<T>` references via `register_property_store<T>(store)` rather than owning or constructing them itself (CLAUDE.md's Architecture Principles: "Dependency injection... to improve testability and flexibility") — whoever composes a capability into a host owns the actual storage and decides its lifetime; `Context` only coordinates access to it. `get<T>()` distinguishes two failure modes deliberately: no store registered for `T` at all is a setup mistake (a capability composed without a property its own contract depends on) and throws `std::logic_error`, while an entity simply lacking a value in an otherwise-registered store is an ordinary, expected outcome and returns `std::nullopt` — the same branch §21's own handler code takes via `.or_else(...)`.

**Open questions (flagging for human review, not silently resolved):**

- Composing capabilities, resolving `contracts.consumes`/`produces`, and reading a host manifest are all out of scope here by design (per the assignment) — `Host` has no notion of a capability graph at all yet. When the manifest-to-C++ generator (`tools/atlas-cgen`) grows this capability, it's an open question whether `Host` itself grows a capability-composition entry point or whether a separate generated layer sits on top of it unchanged.
- `resolve_additive` takes contributions as a `std::span` the caller assembles fresh each time — there is no standing per-entity *contribution registry* yet (something that lets a capability add/remove a named contribution and have it persist between resolutions, per §20's Continuous Re-resolution). This round only needed "resolve once, given a fixed contribution list," which is real but smaller than the standing model §20 describes in full — building the registry is a natural next increment once a scenario needs contributions to change over an entity's lifetime rather than being fixed at setup.

**Provides:** host execution environment, runtime integration, coordination between systems.

## Dependency position

`atlas-runtime` depends publicly on `atlas::entity`, `atlas::scheduler`, and `atlas::stage` (all three appear directly in `Host`'s public interface — its constructor takes a `stage::StageSequence`, its entity methods take/return `EntityRef`, and `schedule()` takes a `scheduler::Job`), plus `atlas_project_options`/`atlas_project_warnings` and the standard library. Per §5, it may depend on further lower-level libraries and generated contracts as those needs arise, never upward on capabilities, applications, or editor/deployment-specific code — consistent with `atlas-runtime` sitting near the top of the runtime-library stack, coordinating the systems beneath it rather than being coordinated by them.
