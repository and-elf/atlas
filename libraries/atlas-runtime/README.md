# atlas-runtime

**Status:** Seeded. Implements `atlas::runtime::Host` (`include/atlas/runtime/host.hpp`) — the concrete runtime object a server or client process actually instantiates to hold state and drive execution. A `Host` owns an `atlas::entity::EntityRegistry` and an `atlas::scheduler::Scheduler` (constructed from an `atlas::stage::StageSequence`), and exposes:

- authority: `has_authority() const` — a plain bool, set once at construction (see Scoping decisions — the open question a previous round of this README left undecided).
- entity lifecycle: `create_entity()`, `destroy_entity(EntityRef)`, `is_entity_alive(EntityRef) const` — each delegating directly to the owned `EntityRegistry`.
- tick execution: `schedule(const StageId&, Job)`, `run_tick() const`, `sequence() const` — each delegating directly to the owned `Scheduler`.

Also implements `atlas::runtime::PropertyStore<T>` (`include/atlas/runtime/property_store.hpp`) — generic per-entity storage for one property type, the storage side of `atlas::Context::get<T>()` — and, in `include/atlas/runtime/property_composition.hpp`: `atlas::runtime::Contribution<T>` (carrying a `Lifetime` tag, a `priority`, and a `weight` alongside its source and value) and all seven of spec §20's composition strategies now have a working evaluator — `resolve_additive<T>`, `resolve_multiplicative<T>`, `resolve_override<T>`, `resolve_priority_override<T>`, `resolve_set_union<T>`, `resolve_ordered_composition<T>`, and `resolve_weighted_composition<T>`.

Also implements, in `include/atlas/runtime/action.hpp`: `atlas::runtime::ActionState` (`Started`/`Ongoing`/`Cancelled`/`Completed` — the lifecycle any request that doesn't resolve within its own call eventually passes through, whether a fixed-duration wind-up or an open-ended external round-trip; a request that *does* resolve synchronously is the degenerate case where `Started` and `Completed` collapse into the same call, which `RequestResult` plus whatever event a handler publishes already models — this doesn't replace that), the `atlas::runtime::Cancellable<T>` concept (a property carrying both `action_state` and `cancel_requested`), `atlas::runtime::request_cancel<T>` (sets the flag; the actual transition to `Cancelled` happens later, inside `advance_action`), and `atlas::runtime::advance_action<T>` (checks `cancel_requested` *before* running the action's own per-tick logic — an already-terminal action is a no-op; a pending cancel transitions to `Cancelled`, runs the caller's `on_cancel` hook, and never invokes `on_advance` at all that call; otherwise runs `on_advance`, which decides for itself when to transition further, the same way `resolve_additive`/`resolve_multiplicative` have no opinion on what a property represents).

Also implements `atlas::Context` (`include/atlas/runtime/context.hpp`) — the typed context a capability's request handler receives, matching spec §21's worked example call-by-call: `ctx.get<T>(entity)` (a monadic `std::optional<std::reference_wrapper<T>>`, reading through a registered `PropertyStore<T>`), `ctx.set<T>(entity, value)` (writes through the registered store, creating the entry if none existed yet — unlike `get<T>()`, which only ever hands back a reference into an entry that already exists), `ctx.reset_property<T>()` (clears every entity's stored value for `T`), `ctx.register_triggered_property_store<T>(store)` (registers `store` exactly like `register_property_store<T>()` and additionally remembers how to reset it), `ctx.end_tick()` (resets every store registered that way, in registration order), `ctx.publish<T>(event)` (synchronous, in-registration-order dispatch to anything that `ctx.subscribe<T>(handler)`'d), and `ctx.host()` (exposing `has_authority()`). Also implements the free function `atlas::advance_tick(Host&, Context&)` (issue #38) — runs `host.run_tick()` then calls `ctx.end_tick()`, the first genuine per-tick entry point tying `Host` and `Context` together, so a triggered property's tick-boundary reset happens automatically rather than a caller calling `reset_property<T>()` by hand for every type. `Context` lives in the top-level `atlas` namespace, not `atlas::runtime` — the same convention `EntityRef`/`RequestResult` already follow — even though the header is physically owned by this library. `Context` is deliberately domain-agnostic: `get`/`set`/`reset_property`/`register_triggered_property_store`/`publish`/`subscribe` are templates operating on whatever `T` a capability's own contract declares, using type-erased (`std::any` keyed by `std::type_index`) maps internally rather than any hard-coded list of known property/event types.

**Scoping decisions:**

- This is deliberately **not** the eventual capability-composed host described in §7 (Host Composition) and §8 (Atlas Hosts) — that version is assembled by Atlas tooling from capability manifests (`depends_on`, `contracts.consumes`/`produces`, §13/§14), and neither the manifest format's code-generation step nor a host manifest reader exists in this repository yet. Building or hand-simulating that layer was explicitly out of scope for this slice. `Host` is instead the hand-composed runtime substrate such a manifest-driven host would eventually sit on top of: the concrete object a process new()'s up today, composed only from systems that already exist for real in this repo (`atlas-entity`, `atlas-stage`, `atlas-scheduler`).
- `Host` is an encapsulated class (private members + delegating methods), not a plain aggregate, even though it adds no invariant of its own beyond what `EntityRegistry` and `Scheduler` already protect internally: its entire reason to exist is to be the single owner composing those two systems, so there is no public field a caller could usefully set directly without going through one of the delegating methods.
- `schedule()`/`run_tick()`/`sequence()` are thin pass-throughs to the owned `Scheduler`, and `create_entity()`/`destroy_entity()`/`is_entity_alive()` are thin pass-throughs to the owned `EntityRegistry` — `Host` adds no additional validation or business logic beyond delegation. This matches the assignment's framing of `atlas-runtime` at this stage: proving out "coordination between systems" using only what already concretely exists, not inventing new behavior ahead of the systems that would need it (request routing, replication, resource resolution — none of which exist yet either).
- **Authority is now decided**: a plain `bool`, required at construction (`Host(stage::StageSequence, bool has_authority)`), never changed afterward. This resolves the open question a previous round of this README left explicitly undecided, once a real call site (a `Context`-based request handler checking `ctx.host().has_authority()`, matching §21's worked example verbatim) existed to design against rather than guess ahead of. A richer representation — distinct `ServerHost`/`ClientHost` types, or a capability-level concern layered on top — remains possible later; this is deliberately the smallest thing that answers the one question §21's handler code actually asks. See Open questions below for what's *not* resolved by this.
- `PropertyStore<T>`/`Contribution<T>`/`resolve_additive<T>`/`resolve_multiplicative<T>`/`resolve_override<T>`/`resolve_priority_override<T>`/`resolve_set_union<T>`/`resolve_ordered_composition<T>`/`resolve_weighted_composition<T>` are deliberately domain-agnostic (spec §2, Mechanism Over Meaning): none of them know what `T` represents, only that it's storable (or, for Set Union/Ordered Composition, that it's a single element or a collection thereof). All seven of §20's composition strategies now have a working evaluator: `resolve_override` resolves to the most-recently-contributed value (or `base` with no contributions); `resolve_priority_override` resolves to the highest-priority contribution, ties breaking toward the later contribution in span order, and implements §20's "Continuous Re-resolution and Preemption" semantics directly — a higher-priority contribution wins as soon as it's part of the resolved span, and a preempted contribution wins again immediately once the contribution that outranked it is no longer part of that span, without either ever being mutated by the resolve call itself; `resolve_set_union` merges `base` with every contribution's collection, de-duplicating by element; `resolve_ordered_composition` returns `base` followed by every contribution's single element in span (contribution) order, without de-duplicating — order is the point; `resolve_weighted_composition` returns the weighted average of every contribution's value, normalized by the total weight (so weights need not already sum to 1), falling back to `base` if the total weight is exactly 0. See `property_composition.hpp`'s per-function header comments for each strategy's spec §20 worked example reproduced as its own test.
- `Contribution<T>` gained a `Lifetime` field (`Permanent`/`Duration`/`UntilEvent`/`WhileCondition`), defaulted to `Permanent` so every existing `{.source = ..., .value = ...}` call site is unaffected — but it's purely descriptive metadata this round, not something any function here branches on. An earlier version of this change also added `remove_contributions_by_source<T>`, reasoning that a `WhileCondition` contribution would need an explicit removal call the instant its governing condition failed, mirroring how `add_contribution`-style functions already push a new entry. That reasoning didn't survive contact with what `WhileCondition` actually means: nothing *fires* an event when a condition like "is the target still in range" stops holding — it's a fact about the current tick, not an occurrence, so there is nothing to react to and no discrete moment to call a removal function at. The correct model is that a `WhileCondition` contribution is never stored at all: it's constructed fresh every tick by whichever capability owns the condition and fed directly into `resolve_additive`/`resolve_multiplicative` alongside whatever `Permanent` contributions are already stored — both already accept a plain `std::span`, so no new primitive was needed once the model was corrected. `remove_contributions_by_source<T>` was reverted before anything used it, rather than merged and left dead; `demo/modules/aura` (see `demo/README.md`'s "Range-based auras") is the real consumer this was built for, and it needed a different function on `movement` instead (`refresh_speed_with_transient_contributions`), not anything added here. `Duration`/`UntilEvent` remain unimplemented: each needs its own associated data (a tick countdown; an event type to listen for) a bare enum tag can't carry, and nothing consumes them yet.
- `Contribution<T>` also gained `priority` (`std::int32_t`, defaulting to 0) and `weight` (`double`, defaulting to 1.0) fields once `resolve_priority_override`/`resolve_weighted_composition` needed them — both default so every pre-existing `{.source = ..., .value = ...}` call site still compiles unaffected, resolving as the lowest-priority candidate and a fully-self-weighted contribution respectively.
- `PropertyStore<T>` required adding a `std::hash<atlas::EntityRef>` specialization to `atlas-entity` (previously only `atlas::ResourceId` had one) so `EntityRef` could key a `std::unordered_map` — combines both fields (index, generation) rather than reusing one directly, since neither field alone is well-distributed the way `ResourceId`'s single already-random hash value is.
- `Context` borrows `PropertyStore<T>` references via `register_property_store<T>(store)` rather than owning or constructing them itself (CLAUDE.md's Architecture Principles: "Dependency injection... to improve testability and flexibility") — whoever composes a capability into a host owns the actual storage and decides its lifetime; `Context` only coordinates access to it. `get<T>()` distinguishes two failure modes deliberately: no store registered for `T` at all is a setup mistake (a capability composed without a property its own contract depends on) and throws `std::logic_error`, while an entity simply lacking a value in an otherwise-registered store is an ordinary, expected outcome and returns `std::nullopt` — the same branch §21's own handler code takes via `.or_else(...)`.
- `ActionState`/`Cancellable<T>`/`request_cancel<T>`/`advance_action<T>` grew out of `demo/modules/cast_time_attack` and `demo/modules/auto_attack` each hand-rolling their own "is this in progress, and did something just cancel it" bookkeeping (an `is_casting` bool plus ad hoc subscriber functions) — once a second, structurally different capability needed the identical shape (one has a genuine one-shot wind-up; the other has a recurring cooldown cycle that restarts itself on completion), the recurring part was worth generalizing here rather than a third capability re-deriving it again. Deliberately *not* a manifest-level feature (a `depends_on: [Cancellable]`-style declaration with tooling-generated state transitions was considered and rejected): atlas-cgen's declarative format expresses structure only, never behavior (spec §14, The Declarative Boundary) — auto-generating "on cancel, transition state" is exactly the kind of behavior that boundary keeps out of YAML. `Cancellable<T>` is a compile-time structural concept instead (the same device `Composable<T>` already is), and `advance_action` is a plain hand-called function, not code generation.
- `ActionState`/`Cancellable<T>` can't live on a manifest-generated property directly yet: the manifest type system has no enum field type (only `float`/`int32`/`uint64`/`bool`/`EntityRef`), so a capability wanting to be `Cancellable` keeps `action_state`/`cancel_requested` in a hand-written companion structure alongside its generated property — the same "capability's own private per-entity bookkeeping" shape `armor::ContributionRegistry`/`movement::ContributionRegistry` already establish. Teaching atlas-cgen a real enum field type is a reasonable future increment but a separate, larger piece of tooling work, not attempted here.
- `PropertyStore<T>::reset()` and `Context::set<T>()`/`reset_property<T>()` are the storage/access primitives spec §20's "Triggered composition has no separate delivery mechanism" needs: a triggered property (an event's occurrence) is a same-tick write via `set<T>()` — there's no pre-existing entry for an occurrence to mutate through the way a continuous property's `get<T>()` reference already assumes — read via the ordinary `get<T>()` every other property already uses, absent-this-tick observed as `nullopt` once `reset_property<T>()` clears it at a tick boundary. This was issue #25's first slice; `ctx.publish<T>()`/`subscribe<T>()` remain unchanged and still work the old, callback-based way — migrating `movement::PositionChanged`/`interruption::ActionInterrupted` and their `auto_attack`/`cast_time_attack` consumers onto `set`/`get`/`reset_property` instead is explicit follow-up (issue #25), not done in this round.
- `Context::register_triggered_property_store<T>()`/`end_tick()` and the free function `advance_tick(Host&, Context&)` (issue #38) close the gap the previous bullet left open: there is now a genuine, single per-tick entry point that resets every triggered property automatically, rather than requiring a caller to call `reset_property<T>()` by hand for each `T` a host composes. This is deliberately **not** the parallel/job-stealing DAG scheduler spec §4 describes in full — `Scheduler::run_tick()` (`atlas-scheduler`) stays single-threaded and strictly sequential, unchanged; `advance_tick` only adds the missing tick-boundary reset on top of it. A free function rather than a `Host` method: `Host` and `Context` are deliberately decoupled siblings (see the capability-graph open question below), and `Context` already depends on `Host` (its constructor takes a `Host&`), so a function needing both types lives alongside `Context` rather than making `Host` include `context.hpp` and create a circular header dependency.

**Open questions (flagging for human review, not silently resolved):**

- Composing capabilities, resolving `contracts.consumes`/`produces`, and reading a host manifest are all out of scope here by design (per the assignment) — `Host` has no notion of a capability graph at all yet. When the manifest-to-C++ generator (`tools/atlas-cgen`) grows this capability, it's an open question whether `Host` itself grows a capability-composition entry point or whether a separate generated layer sits on top of it unchanged.
- `resolve_additive` takes contributions as a `std::span` the caller assembles fresh each time — there is no standing per-entity *contribution registry* yet (something that lets a capability add/remove a named contribution and have it persist between resolutions, per §20's Continuous Re-resolution). This round only needed "resolve once, given a fixed contribution list," which is real but smaller than the standing model §20 describes in full — building the registry is a natural next increment once a scenario needs contributions to change over an entity's lifetime rather than being fixed at setup.
- **Property-graph/SoA execution model (issue #129) — storage and dispatch questions the spec doesn't settle.** §4/§5/§20 already specify the *behavior* this needs (node readiness from the provides/consumes graph, permission to batch/vectorize internally, triggered composition as a same-tick property read with no separate delivery mechanism) — that part of #129 is written. What's still undecided is the mechanical layer underneath `PropertyStore<T>`:
  - **Storage layout.** `PropertyStore<T>` is one `std::unordered_map<EntityRef, T>` per property type today — entity-keyed, not columnar. A batched/vectorized transform ("run once over every entity that has this property," per §4's Tick Execution) needs a contiguous, SoA-shaped column instead. Not designed yet.
  - **Sparse entity membership.** Not every entity has every property — that's the whole reason `PropertyStore<T>` is a map rather than an array indexed by entity slot. A dense column for vectorization has to represent a membership set that changes as entities are created/destroyed/gain-or-lose properties, without falling back to per-entity branching inside the batch. This is the classic ECS archetype-vs-sparse-set design problem, and it hasn't been addressed anywhere yet — not in this repo, not in #129's own text. It has to be answered before `PropertyStore<T>`'s replacement can be designed, not as a follow-up to it.
  - **Node dispatch/registration.** A graph node's transform needs to be resolved by the `PropertyId` it provides, not called by capability-symbol name the way internal dispatch works today (see #141) — otherwise substituting a node's implementation would require the same source-level edit #141 already flags as a gap on the request side. The natural shape is a compile-time descriptor, generated from a capability's `provides:`/`consumes:` declarations, binding those `PropertyId`s to a hand-written transform function with a fixed batch signature — but the actual function signature and registration mechanism aren't designed. #141's own framing undersells this, though: §5 already treats capabilities themselves as substitutable graph nodes ("properties and capabilities as nodes"), so the gap is that today's demo code (concrete calls like `health::on_apply_damage()`) bypasses that model, not that no substitution point could exist in principle.
  - **Capabilities are graph nodes too, not just properties — relational, multi-entity logic belongs in the graph at that level, not outside it.** A capability like `line_of_sight` (evaluating a relationship between whichever entities a request names as attacker/target/obstacle) isn't excluded from the graph just because it doesn't own one property outright. §5 already frames the graph as "properties and capabilities as nodes," and §4's Tick Execution explicitly processes the tick's input batch (requests) through the same capability dependency graph as properties. "Check range, then enter the line-of-sight node, then apply damage" is ordinary capability-dependency ordering — ordinary graph scheduling, not something the model excludes. What's actually undesigned is narrower than "is this graph-eligible" (it is) — see the next bullet.
  - **Gather and compaction — two primitives the graph model needs for capability-level nodes that pure per-entity property nodes never did.** A property node like the ones above reads only its own row's inputs. A relational node like `line_of_sight` needs another entity's `Position` — whichever entity a request's `attacker`/`target`/`obstacle` field names — which is a gather (an indexed cross-row read), not a same-row elementwise read. And when a node like a range check fails, the request doesn't proceed to the next node at all — the batch has to shrink between stages (compaction/filtering), unlike a property node, which always produces exactly one output per input row. Neither primitive exists in `PropertyStore<T>` or is addressed by #129's current scope; both are prerequisites for batching/vectorizing capability-level graph nodes, not just property-level ones.
  - **In-place mutation is safe, and doesn't need double-buffering** — this much followed from what's already true: §5 requires exactly one provider per non-aggregated property (no write-write races on a column, ever), and §4's node-readiness scheduling is a hard barrier (a consumer never runs until every property it consumes has reached its tick value). Together those mean an elementwise transform (`output[i]` computed from `input[i]` alone, no cross-entity coupling within the node) can safely write its output back into the same storage its input came from.
  - **No previous-tick memory belongs in this store, for any reason.** Raised initially for render interpolation (#64) — resolved there by concluding the store shouldn't carry history at all: a presentation layer can extrapolate from current-tick state alone given a rate-of-change (`Velocity`-shaped) property, and even genuine two-sample interpolation is a presentation-only concern (§4) that can keep its own client-local cache outside the authoritative store. See #64's comment thread for the full reasoning.
  - **Vectorization should be compiler auto-vectorization of the elementwise batch loop, not hand-written SIMD intrinsics.** AVX doesn't exist on ARM, and this project targets macOS/Apple Silicon as a first-class platform (CLAUDE.md) — hand-rolled AVX won't compile there. Letting each target auto-vectorize to its own ISA (AVX2/AVX-512 on x86-64, NEON on Apple Silicon) is portable, but shifts the open risk to whether different auto-vectorized ISAs produce bit-identical results — an empirical question for #110 (Determinism verification tooling) to answer before this is relied on, not an assumption to build on.
  - **Deterministic ordering of the shared `Random` stream under real parallel execution needs an answer, and there's a zero-new-primitive one.** §4 requires the per-host random stream to be "consumed in the same fixed order the deterministic scheduler already guarantees" — but if two independent graph nodes both draw from it and genuinely run on separate threads, "same fixed order" can't be a function of which one happens to finish first. Rather than inventing a new ordering primitive (an explicit "producer runs before producer" annotation was considered and rejected — it reintroduces exactly the separate stage/ordering concept §5's "Ordering Without Stages" argues isn't needed, and unless expressed as a graph edge rather than a named reference, it reintroduces capability-name coupling the `provides:`/`consumes:` model was built to avoid), model the stream's cursor as an ordinary property: whoever draws next both consumes and re-produces it, same as any other property, so ordering falls out of the existing dependency graph with no new mechanism. The honest cost: every node touching `Random` is fully serialized relative to every other one (there's only one cursor instance, host-wide, not one per entity — that's *why* this forces a strict order rather than an entity-scoped one), so parallel dispatch buys nothing among them; they might as well run on one thread. That's a real parallelism cost, but likely a small one, since RNG-touching nodes should be a minority.
  - **This only fixes ordering *between* nodes — a single node's own batch still needs a canonical order for the entities *within* it**, if it draws more than once per call (e.g. one node rolling a crit chance for every attack landed this tick). §4 already bans "unordered iteration over concurrent or parallel work," so this isn't a new gap, just a rule implementers have to actually honor inside a node's own batch loop. For a node driven by a tick's request batch, the right order is the batch's own arrival sequence — §4 already guarantees requests within a batch are ordered deterministically ("e.g. arrival sequence"), so a request-driven node can reuse that existing order at zero extra bookkeeping cost, and it doesn't need to persist past the tick it belongs to (ephemeral, alongside the batch itself, not written into `PropertyStore<T>`). A node that isn't driven by any request at all — a periodic per-entity effect iterating "every entity that currently has property X" — has no request-arrival sequence to borrow, and would need a different canonical order instead (entity creation order being the natural candidate, since entity creation is itself already a deterministic sequence); this isn't designed and shouldn't be assumed to be the same answer as the request-driven case.
  - This also bears on #94 (where capability-graph composition lives on `Host`), #95 (standing per-entity contribution registry), and #99 (property replication strategies): each would likely be designed against the wrong storage shape if built before this is settled.
- **`ctx.publish<T>()`/`ctx.subscribe<T>()` still exist and are still used for occurrences that, per §20's post-#25 "no separate delivery mechanism" position, are now candidates for the same `set`/`get`/`reset_property` triggered-property migration `movement::PositionChanged`/`interruption::ActionInterrupted` already went through. `demo/`'s remaining seven `events:` blocks (`AutoAttackLanded`, `CastStarted`, `CastLanded`, `HealthChanged`, `ArmorEquipped`, `DotEffectTicked`, `PathTargetReached`) all still dispatch via `ctx.publish<T>()` — see issue #131's audit. Nothing yet tracks whether `publish`/`subscribe` should eventually be deprecated as an API once that migration is complete, or kept for some category of occurrence that genuinely doesn't fit a triggered property — that category, if one exists, hasn't been identified yet.

## Dependency position

`atlas-runtime` depends publicly on `atlas::entity`, `atlas::scheduler`, and `atlas::stage` (all three appear directly in `Host`'s public interface — its constructor takes a `stage::StageSequence`, its entity methods take/return `EntityRef`, and `schedule()` takes a `scheduler::Job`), plus `atlas_project_options`/`atlas_project_warnings` and the standard library. Per §5, it may depend on further lower-level libraries and generated contracts as those needs arise, never upward on capabilities, applications, or editor/deployment-specific code — consistent with `atlas-runtime` sitting near the top of the runtime-library stack, coordinating the systems beneath it rather than being coordinated by them.
