# atlas-ui

**Status:** Seeded (issue #29, "minimal TDD scaffold" — a deliberate scoping decision, not the library's full eventual surface). Implements the four primitives §19 (Minimum UI Contract) names as the platform's minimum UI contract:

- `atlas::ui::Node` (`include/atlas/ui/node.hpp`) — a positioned/sized tree element (`atlas::ui::Transform2D`, `include/atlas/ui/transform.hpp`), owning `children` by value, with a bindable `visible` flag, a bindable `resource` reference, and an optional `Clickable` behavior.
- `atlas::ui::BindableProperty<T>` (`include/atlas/ui/bindable_property.hpp`) — the bindable-property mechanism. This resolves against the **real** property composition machinery in `atlas-runtime` (`atlas::Context::get<T>()`, `atlas::runtime::PropertyStore<T>`), not a parallel UI-only stub: a `BindableProperty<T>` either holds a literal fallback value or a `bound_entity`, and `resolve(ctx)` reads straight through `ctx.get<T>(*bound_entity)` when bound. There is no caching between calls — re-reading the store on every `resolve()` call is what satisfies §20's Continuous Re-resolution ("re-evaluated whenever that property's effective value changes") without needing a push/invalidation channel.
- Resource references — a resource-typed `BindableProperty<atlas::ResourceId>` (e.g. `Node::resource`) binds exactly the same way any other property does (§20: "Resources compose exactly like properties"); no separate resource-binding mechanism was needed.
- `atlas::ui::Clickable` (`include/atlas/ui/clickable.hpp`) — the one behavior this pass implements, per the issue's explicit "Clickable is the natural minimal choice" framing. `invoke(ctx, source)` resolves its own `enabled: BindableProperty<bool>` against `ctx` and returns an `atlas::input::Intent{.id = intent, .entity = source}` unless disabled, in which case it returns `std::nullopt` (explicit rejection, never silent coercion — the same posture §6 takes toward request validation, applied here to behavior invocation instead). `intent: atlas::input::IntentId` is Clickable's own authored field — which semantic intent a click on this node produces, matching §19's `AbilitySlot` example's `on_click: intent: CastAbility`. `Node::try_click(ctx, source)` additionally gates on the node's own `visible` before delegating to `clickable->invoke(...)` — a hidden node cannot be clicked even if its `Clickable` is itself enabled.
- `atlas::ui::Layer` (`include/atlas/ui/compositing.hpp`) — the nice-to-have from §19's Compositing Layers: just the `World`/`Hud`/`Menu` ordering enum (scoped enums already order by declaration position, so no `operator<=>` override was needed). Not the compositing/rendering engine itself — see Deferred below.

**Provides:** UI node tree, property binding infrastructure, behavior primitives (`Clickable` implemented; `Focusable`/`Draggable`/`Tooltip`/`CooldownOverlay` not yet). Backend dispatch and compositing-layer *implementation* are explicitly deferred (see below).

**Spec:** [§19 UI System](../../docs/specification/19-ui-system.md) (Minimum UI Contract — the four primitives this library implements), [§20 Property and Resource Composition](../../docs/specification/20-property-and-resource-composition.md) (Continuous Re-resolution — what `BindableProperty::resolve()` implements; Resource Composition — why resource references reuse the same mechanism), [§13 Library Architecture](../../docs/specification/13-library-architecture.md#library-responsibilities) (responsibility), [§5 Dependency Model](../../docs/specification/05-dependency-model.md) (dependency rules)

## Scoping decisions

**Real integration, not a parallel property system.** The assignment's central instruction — "actually resolves against atlas::runtime's real property store/composition machinery... integrate for real, don't invent a parallel stub property system" — is what `BindableProperty<T>::resolve(atlas::Context&)` is built around: it is a thin, generic wrapper around `Context::get<T>()`, nothing more. A UI node binding to a composed `MovementSpeed` and a movement capability reading `MovementSpeed` read the exact same `PropertyStore<MovementSpeed>` through the exact same typed accessor — there is no UI-specific notion of "what a property is" anywhere in this library. This does mean `BindableProperty<T>` inherits `Context::get<T>()`'s own failure-mode split: binding to an entity with no stored value for `T` is an ordinary, expected outcome (falls back to the literal `value`), while binding when no `PropertyStore<T>` was ever registered at all is a setup mistake and propagates `Context::get<T>()`'s `std::logic_error` rather than silently falling back — the same distinction `Context` itself already draws, not a new one invented here.

**One behavior, not a behavior framework.** Only `Clickable` is implemented. `Node` carries it as a single `std::optional<Clickable> clickable` field rather than a type-erased list of arbitrary behaviors, because a real multi-behavior mechanism (how `Tooltip` and `CooldownOverlay` coexist on one node, whether behaviors need their own ordering) doesn't have a second real behavior to design against yet — inventing that shape now would be guessing ahead of a concrete second case, the same reasoning `property_composition.hpp`'s README gives for not implementing five composition strategies it has no consumer for yet. Adding `Focusable`/`Draggable`/`Tooltip`/`CooldownOverlay` is a natural next increment once something needs them; whether `Node` then grows a second `std::optional<...>` field per behavior or switches to a generic behavior list is an open question for whoever adds the second one.

**`Clickable` produces `atlas::input::Intent` directly — no separate `ClickEvent` type.** Spec §19 says the UI renderer "produces `Intent` events — the same `Intent` events `atlas-input` produces from hardware input." Both libraries were originally designed concurrently in separate worktrees, so an earlier pass of this library used a local `ClickEvent` stand-in (`{ atlas::EntityRef source; }`) rather than guess at `atlas-input`'s not-yet-existing `Intent` shape. Now that `atlas-input::Intent` exists (`{ IntentId id; EntityRef entity; float axis; }`, matching spec §5's own documented shape apart from `axis` staying a plain float — no `Vec2` type exists in this codebase yet), `Clickable::invoke()` produces one directly: `atlas::input::Intent{.id = intent, .entity = source}`. `ClickEvent` has been removed entirely. This makes §19's "a button click and a keypress are indistinguishable to the capabilities below them" literally true rather than aspirational — `atlas-ui` now has a real, public, downward dependency on `atlas-input` for this shared vocabulary type.

**Node identity is not modeled.** There is no `NodeId`/handle concept — `Node` owns its children by value (`std::vector<Node> children`), and `Clickable`/`ClickEvent` reference whichever `atlas::EntityRef` the caller supplies as the click's "owner," not the node itself. A stable, externally-addressable node identity (e.g. so a bridge capability could say "node #42 was clicked" from outside the tree) is a real future need but wasn't required to prove out the four primitives this pass targets, so it isn't guessed at here.

**Resource references reuse `BindableProperty`, not a separate mechanism.** §20 states resources "compose exactly like properties," so `Node::resource` is simply `BindableProperty<atlas::ResourceId>` — no second binding type was needed. `Node` exposes exactly one generic `resource` slot rather than named fields (`icon`, `background`, `font`, as §19's own examples list) — a real widget vocabulary (a future `Button`/`AbilitySlot`-style UI Capability Package, §19) would likely want several independently-named resource-typed fields, which is exactly the kind of widget-specific vocabulary this pass leaves to that future package rather than inventing now on a bare `Node`.

## Out of scope this pass (deferred, per the issue)

- **Backend dispatch / rendering.** No GPU-native, editor-native, web, or terminal backend integration (§19, Backend Implementations) — that's `atlas-render`'s and later host-composition's job. `Node`/`BindableProperty`/`Clickable` are pure data + resolution logic; nothing here walks a tree and issues a draw call.
- **Compositing-layer implementation.** `atlas::ui::Layer` (`World`/`Hud`/`Menu`) is only the ordering enum — a nice-to-have per the issue's own framing ("not required"). The actual compositing engine (per-layer Ordered Composition of widget stacking, §19) is not implemented.
- **Higher-level widget vocabularies** (`Button`, `InventoryGrid`, `Timeline`, `Inspector`, and the `Focusable`/`Draggable`/`Tooltip`/`CooldownOverlay` behaviors) — per §19, these are "UI Capability Packages," separate from the core primitive contract this library provides.
- **Art style vs. player styling** (§19) and the WotLK addon compatibility layer (§19) are both later, separately-scoped capabilities built on top of this primitive contract, not attempted here.
- **UI replication exemption.** §20 states UI capability properties are never replicated, since the server never composes UI capabilities at all. Nothing in this library enforces or tests that exemption directly — it falls out of `atlas-ui` simply not being a dependency any server-composed capability would pull in, the same way `atlas-input`/`atlas-editor` stay absent from a headless server host (§13).

## Open questions (flagging for human review, not silently resolved)

- Whether `Node` should grow a generic, type-erased behavior list once a second behavior (`Focusable`) is implemented, versus continuing to add one `std::optional<Behavior>` field per behavior as this pass does for `Clickable` alone.
- Whether `Node` eventually needs a stable identity (`NodeId`) independent of the `atlas::EntityRef` behaviors currently take as an ad hoc "source" parameter — deferred until a real caller (e.g. a UI-to-addon bridge capability, mirroring §19's `health-ui-bridge` worked example) needs to reference a specific node from outside the tree.
- Whether a single generic `Node::resource` slot is the right primitive-level shape long-term, or whether even the core `Node` (not just future widget packages) should carry more than one named resource-typed field — left open since nothing in this pass needed more than one.

## Dependency position

`atlas-ui` depends publicly on `atlas::entity` (for `atlas::EntityRef`, which `BindableProperty<T>::bound_entity` and `Clickable` reference directly), `atlas::input` (for `atlas::input::Intent`/`IntentId`, which `Clickable::invoke()` now produces directly rather than a local `ClickEvent` stand-in — see Scoping decisions above), `atlas::resource` (for `atlas::ResourceId`, `Node::resource`'s value type), and `atlas::runtime` (for `atlas::Context`/`atlas::runtime::PropertyStore<T>`, which `BindableProperty<T>::resolve()` reads through) — `atlas::core` comes in transitively through those. Per §5, it may depend on further lower-level libraries and generated contracts as those needs arise, never upward on capabilities, applications, or editor/deployment-specific code. Per §13, `atlas-ui` is one of the three optional libraries (alongside `atlas-input` and `atlas-editor`) — a headless server host never composes it, and composing none of the three costs a game nothing (§16, Capability Independence).
